# 性能实测 · BENCHMARK

> 怎么在**客户的机器上**出一份可以进合同的性能报告。
> 对应任务卡 T-110 · 配套 [附件A_数字资产规范_草案.md](附件A_数字资产规范_草案.md)

---

## 为什么必须在客户机器上测

我们这边测出来的数字，对验收没有意义。原因有三条，每条都足以让数据作废：

1. **显卡差一个数量级。** 集成显卡与独立显卡在同一场景上能差 5–10 倍；
2. **硬件加速可能是关的。** 企业统一镜像里禁用 GPU 加速并不罕见，届时浏览器退回软件
   渲染（SwiftShader），帧率数据完全不可比；
3. **浏览器内核可能偏旧。** v0 需要 WebGL 2（[ADR-0013](adr/0013-v0-不支持-webgl1.md)）。

所以 benchmark 做成了一个**独立单页**：拖进去一个 `.w3p` 就能出报告，不需要装编辑器、
不需要联网、不需要我们在场。

---

## 怎么用

1. 把 `packages/player/dist/` 整个目录拷到客户机器上（或部署到内网任意静态服务器）；
2. 用支持 WebGL 2 的浏览器打开 `bench.html`；
3. 把要测的 `.w3p` 拖进页面（或点「选择 .w3p」）；
4. 等约 6 秒——期间相机自动环绕，这是刻意的：静止画面会让驱动跳过工作，测出一个
   用户永远体验不到的帧率；
5. 点「复制为 Markdown」，把结果贴进工单；
6. 再点「下载 JSON」，把那个文件放进 `docs/bench-reports/`——
   [附件A](附件A_数字资产规范_草案.md) §7 由脚本从它回填，**不是从 Markdown 里抄**。

前 30 帧会被丢弃：着色器编译和贴图上传都发生在那里，与稳态性能无关。

## 报告里的每一项是什么

| 指标 | 含义 | 阈值来源 |
|---|---|---|
| **平均帧率** | 连续渲染时的帧率 | 经验值：45 fps 黄灯 / 25 fps 红灯。**尚无目标机器实测** |
| **P95 帧时间** | 每 20 帧里最慢的那一帧 | 经验值：33 ms 黄灯 / 66 ms 红灯 |
| **最慢单帧** | 仅供参考 | — |
| **三角面数** | 一帧实际提交的三角形 | `DEFAULT_POLICY.maxTriangles` = 300,000 |
| **Draw call** | 一帧的绘制批次 | 经验值 1,200。**无实测来源**，报告里已注明 |
| **贴图显存（估算）** | 按 RGBA8 + 完整 mip 链推算 | `DEFAULT_POLICY.maxTextureBytes` = 128 MB |
| **几何体 / 贴图 / 着色器** | 常驻显存的对象数量 | 无阈值，用于横向比较两个模型 |
| **承载上限（逐级加载）** | 把整个场景复制 ×1/×2/×4/×8 同时渲染，加到跌破帧率为止 | 帧率阈值同上。压的是 drawcall 与顶点吞吐，**不压显存**（[ADR-0016](adr/0016-逐级加载压力测试的含义.md)） |
| **首屏 · 解包 / 建场景 / 首帧 / 合计** · v1.0 | 打开一个包到画出第一帧，分三段 | **无阈值来源**，见下 |
| **动态灯上限（无阴影）** · v0.5 | 0/1/4/8 盏动态灯，不投影 | 帧率阈值同上 |
| **动态灯上限（low / medium / high 阴影）** · v1.0 | 同上，但开阴影，**三档各一行** | 帧率阈值同上。**与上一行分开报**，理由见下 |
| **建议出厂默认阴影档** · v1.0 | 这台机器上默认该开哪一档 | 取「还带得动 ≥1 盏投影灯」的最高一档 |
| **阴影贴图显存（估算）** · v1.0 | `投影灯数 × 贴图边长² × 4 字节` | 边长读 `shadowMapSizeFor`（512 / 1024 / 2048） |

### 关于「平均帧率」和「P95 帧时间」

只看平均帧率会漏掉最影响体感的问题。一个场景以 60 fps 运行、每秒卡一下 400 ms，
平均下来仍然好看，而用户描述的是「时不时卡一下」。**那种卡顿只出现在 P95 和最慢单帧里。**

### 关于两个「动态灯上限」为什么分开报（v0.5 · T-174）

灯数与阴影是**两种不同的代价**，混成一个数字会让人得出「灯很慢」然后干脆不用灯：

- **多一盏灯**：多一份逐像素的着色计算，代价**平滑上升**；
- **多一盏投影灯**：多一整遍深度 pass，代价**阶梯式上升**。

同一台机器上，「能开几盏灯」和「能开几盏带阴影的灯」经常差好几倍——而这个倍数，
正是排一个场景时最需要知道的数。所以报告里是两行，不是一行。

### 关于三档阴影为什么必须都测（v1.0 · T-279）

到 T-279 之前，bench 页测的是 `['off','medium','high']`，而 `ShadowQualitySchema` 的
三档是 **low / medium / high**。也就是说 **`low` 是一档用户选得到、报告里永远没有数的
设置**——而它恰好是低配机器上唯一可能跑得动的那一档。

**测的档必须等于文档能表达的档。** 现在 `SHADOW_MODES` 从 `SHADOW_QUALITIES` 派生，
schema 加一档它自己就跟着加。

结论行也从两条变成四条（off + 三档）。少了第三个数，「出厂默认该开哪一档」这个问题
在报告里根本**没有可比较的对象**——这是遗留决议 S3 一直悬着的原因。

### 关于「建议出厂默认阴影档」（v1.0 · T-279）

规则一句话：**取「至少还带得动 1 盏投影灯跑在 45 fps 以上」的最高一档；一档都不行就
建议关闭。**

门槛是 1 盏而不是 4 盏，因为默认档回答的是「开还是不开」，而一盏投影灯是「阴影这个
功能开着」的最低成立条件。带不动 1 盏就该默认关——给用户一个开着但一开就掉帧的默认值，
比默认关掉更糟，因为**他不会把掉帧归因到这个开关上**。

### 关于首屏加载时间为什么三段分开报（v1.0 · T-279）

三段各有各的成因，而合起来那个数没有任何可操作性：

| 段 | 慢了意味着 |
|---|---|
| 解包 | 包大，或者机器 IO 慢 |
| 建场景 | 几何 / 贴图多 |
| 首帧 | 着色器编译——**与材质种类数相关，与面数关系不大** |

客户说「打开要好几秒」时，只有分段的数能回答「该改模型还是该换机器」。

四行的 `limit` 一律是 `—`：**这四个数没有阈值来源**。可接受的首屏时间取决于包多大、
网络在哪一端、客户的耐心，没有一条能写进合同的通用线。报一个编出来的阈值比不报更糟,
它会被当成实测结论引用。

### 关于「贴图显存（估算）」

报告里写的是估算，不是测量。GPU 的实际分配取决于驱动的内部格式、压缩与对齐，
而 WebGL 不暴露这些。这个数字给的是正确的数量级和可靠的相对比较，仅此而已。

### 软件渲染

检测到软件渲染时，报告顶部会强制加一段警告，且导出的 Markdown 里也带着：

> ⚠️ 本次为软件渲染（未启用硬件加速或无独立显卡）。帧率类数据**不可作为验收依据**，
> 仅可用于同一台机器上不同模型之间的相对比较。

这段话删不掉，是刻意的（`e2e/tests/bench.spec.ts` 有一条断言盯着它）。

导出的 JSON 里也写着 `capability.level`，**回填脚本据此拒绝把软渲报告写进附件A**。
只写在 Markdown 的那段中文里的话，脚本只能去正则匹配一段措辞——而措辞一改，拒绝就
失效了。

## 当前状态

**尚无目标机器实测数据。** 下面这份是**开发机**的记录，用途只有一个：证明这几档确实
跑得起来、报告确实出得来。**不可作为验收依据**，理由就是本页开头那三条。

### 开发机一轮（2026-08-01）

| 项 | 值 |
|---|---|
| CPU | Intel Core i9-14900HX |
| 内存 | 34 GB |
| 系统 | Windows 11 |
| 渲染 | **SwiftShader 软件渲染**（CI 与本仓库开发环境均无硬件加速） |
| Player 体积 | gzip **243.0 KB / 400 KB**（`pnpm size`，与显卡无关，**这一项可信**） |
| 帧率类 / 灯光档 / 阴影档 | **未记录数字** |

帧率、承载上限、动态灯上限这几档**故意留空而不是填软渲数字**。软件渲染下的帧率与
真实 GPU 无可比性，填进去只会变成一个将来被人引用的错数字——
「一份带错数字的合同附件，比一份留白的危险得多」这句话对这里同样成立。

`pnpm size` 那一行是唯一与显卡无关的量，所以它是这一轮唯一被记下来的数字。

本仓库的开发与 CI 环境只有 SwiftShader 软件渲染，帧率数据无参考价值，因此
[附件A](附件A_数字资产规范_草案.md) §7 的性能指标表**留空**而不是用软渲数据填充。
一份带错数字的合同附件，比一份留白的危险得多。

拿到目标机器后，回填这条路是**脚本走的**（v1.0 · T-280），不是手抄：

1. 在目标机器上跑一遍本页面，点「下载 JSON」；
2. 把文件放进 `docs/bench-reports/`，命名 `<档位>-<代号>.json`——
   档位取 **M1 / M2 / M3**（对应下面「建议至少测三种配置」的三行），代号是这台机器
   在合同里的称呼，例如 `M2-车间工控机.json`；
3. `node scripts/apply-bench-report.mjs`；
4. 提交。`pnpm verify` 里的 `--check` 从此盯着这张表**逐字节**——手改一个字就红。

两条脚本里写死的规则，值得在这里重复一遍：

- **软渲报告会被拒绝**（退出 1，不是警告）。软渲帧率与真实 GPU 没有可比性，填进合同
  附件就是一个将来会被引用的错数字。
- **一档硬件一份报告，不做插值**（§7 回填规则 5）。同一档位放两份文件会直接报错，
  而不是挑一份或者取平均。

四行全部变成 `[实测]` 之后，此段删除。

### 建议至少测三种配置

| 配置 | 为什么 |
|---|---|
| 客户实际使用的主力机型 | 验收依据 |
| 客户机型里配置最低的一台 | 决定我们敢承诺什么 |
| 一台关闭硬件加速的机器 | 摸清最坏情况下用户看到什么 |
