## 趋势观察点

1. **新增动作所需改动文件数**是否仍是 2。一旦涨到 4，说明 C5 的抽象开始漏，通常表现为

   查不出"构建过程需要联网"。

### 趋势观察点

1. **E2E 步数仍然是最有说服力的主指标。** 上一版 9 步时，`pnpm verify` 全绿而

6. **存活发现里有 5 条是「测试断言不到点上」。** 也就是它们保护的功能改坏了也不会红。

## v0.5 · 规模性能（T-184）

`node scripts/bench-scale.mjs [节点数]`。**纯 CPU，没有渲染器**——和 `bench.html`
（T-110，测显卡、必须在客户机器上跑）是两件事。这里全是数组与 Map 运算，任何机器上
结论一致，所以数字可以进仓库、阈值可以当门槛。

单位 ms，20 次取平均，本机 Node 24：

| 操作 | 1000 节点 | | 4000 节点 | | 何时触发 |
|---|---|---|---|---|---|
| | 修复前 | 修复后 | 修复前 | 修复后 | |
| `buildIndex` | 6.78 | **0.25** | 100.00 | **0.80** | 每次结构性编辑 |
| `checkIntegrity` | 4.97 | **0.49** | 62.12 | **1.94** | 每次 commit 后状态栏 |
| `walkTree` | 4.46 | **0.12** | 57.06 | **0.46** | 可达性检查 |
| 删一个节点后重建索引 | 6.77 | **0.10** | 106.13 | **0.61** | 删除对象 |

**修复前每一项都是 O(n²)：节点翻一倍，耗时翻四倍。** 根因只有一个，出现在四个地方——
`getChildren` 是一次全表扫描，而需要「很多个节点各自的孩子」的代码都在循环里调它。
改成一次分组（`groupChildren`）之后全部变成线性。

4000 节点删一个对象从 106 ms 降到 0.61 ms。106 ms 是六帧，用户看到的是点一下删除、
界面卡一下——而且卡顿随导入模型的规模平方增长，正好在「客户拿真实装配体来试」的时候最明显。

`packages/schema/test/scale.test.ts` 守着这条线，**断言的是形状不是毫秒**：同一操作在
n 和 2n 上各测一次，比值必须 < 3（线性约 2，平方约 4）。CI 机器上的墙钟阈值只会教会
团队反复重跑直到变绿，那时它就不再是门槛了。

### 这一轮的方法学教训

**两条变异是绿的，两条都是测试自己的毛病，不是被测代码的：**

1. 「不排序」变异测不出来——生成的基准文档恰好本来就按 `order` 排好，排序是个空操作。
   兄弟节点乱序只在树里拖过之后才出现，而那正是搞错了会让面板和文档打架的时刻。
2. 「父级不存在的节点被丢弃」变异测不出来——孤儿节点是用**新建的顺序 id 工厂**造的，
   于是它的 id 和已有的某个根节点撞了，断言找到的是那个根。

两条测试读起来都完全正确。**没有变异检验，这张卡会带着两条假绿收工。**
