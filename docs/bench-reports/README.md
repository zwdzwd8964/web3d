# 目标机器实测报告

这个目录收 bench 页面导出的 JSON。**它今天是空的**，这不是遗漏——见
[BENCHMARK.md](../BENCHMARK.md) 的「当前状态」一节。

## 放什么进来

只放 bench 页面「下载 JSON」按钮产出的文件，**改过名之后**。命名规则一句话：

```
<档位>-<这台机器的名字>-<场景>-<日期>.json
```

开头必须是 `M1-` / `M2-` / `M3-`，`scripts/apply-bench-report.mjs` 按 `^(M[123])-(.+)$`
解析它。完整的操作步骤在 [BENCHMARK.md §拿到机器之后的 30 分钟](../BENCHMARK.md)，
那一节是写给现场同事的，可以直接打印出来交给他。

## 三个档位

| 档位 | 是什么 | 进不进合同附件 A §7 |
|---|---|---|
| **M1** | 客户主力机型 | **进**。验收依据 |
| **M2** | 客户机型里最低配的那台 | **进**。它决定我们敢承诺什么 |
| **M3** | 关掉硬件加速的机器 | **不进**。它按定义就是软件渲染，回填脚本会拒绝它 |

M3 不进附件不是脚本的缺陷，是刻意的：软渲帧率与真实 GPU 没有可比性，填进合同附件就是
一个将来会被引用的错数字。M3 的结论写进 [IMPL_NOTES.md](../IMPL_NOTES.md)。

## 放进来之后

```bash
node scripts/apply-bench-report.mjs          # 回填附件 A §7
node scripts/apply-bench-report.mjs --check  # 逐字节比对，pnpm verify 里一直在跑
```

`--check` 比对的是**重新生成一遍再逐字节比**，不是「文件在不在」。附件 A §7 那四行是
合同里的性能承诺，手改一个字就红——因为手改的那个字会进合同。

## 为什么这个目录里有个 README 而不是直接空着

`.gitkeep` 保得住目录，保不住上下文。半年后有人看到一个空目录，第一反应是「这里本来
应该有东西吧」，然后要么去翻 git log，要么就当它不存在。
