# 附件A · 数字资产规范（草案）

> **性质**：合同附件草案。本文件的用途是把「性能验收」变成一件双方事先能对齐的事——
> 交付方按此规范提供模型，我方按此规范承诺表现。**超出本规范的资产，其运行表现不作为验收依据。**
>
> **来源约定**：每一行数值都标注来源。四类：
> - `[代码]` —— 来自 `packages/core/src/assets/policy.ts`，导入体检**当场机械执行**，改一个数就要改这份文档
> - `[规范]` —— 来自 [SCHEMA_SPEC.md](SCHEMA_SPEC.md) / [MVP_V0_孵化规划.md](MVP_V0_孵化规划.md) 的明文条款
> - `[待实测]` —— **尚无实测来源**，需在目标机器上跑 [BENCHMARK.md](BENCHMARK.md) 后回填
> - `[实测]` —— 已在目标机器上实测并按 §7 的回填规则写明前提（产品拍板 P-16）；无前提的实测数字不算数
>
> **本草案不含任何拍脑袋的数字。** 凡是没有来源的，标了 `[待实测]` 并留空，没有用估计值填充。
>
> 对应任务卡 T-113 · 技术方案 R01 · 合同 §6.3

## 0. 为什么需要这份文档

技术方案 R01 把它说清楚了：**客户的 CAD 导出件是唯一没有任何架构能解决的问题。**
一个 800 万面、带 60 张 4K 贴图的装配体，在任何引擎里都会卡；届时讨论的不会是
「这个模型超标了」，而是「你们的产品性能不行」。

这份附件把那场讨论提前到签约前。它同时是技术保险和商务保险。

### 「允许」与「代做」的分界（2026-08-03，产品拍板 P-14）

上表两行里的「允许」只有一个含义：**送检件可以是压缩过的，我方能正确读取并解码。**
压缩这件事在导出环节由送检方完成。**我方不承担把未压缩资产压成 KTX2 的转码服务**——
v1.5 的服务端资产转码**只做 Draco 几何压缩**（纯 WASM，无服务端原生二进制），不含 KTX2 贴图编码。
理由：KTX2 编码需要服务端原生二进制并锁定单一 CPU 架构（amd64），与技术方案 §3.2-4
「服务端不依赖 GPU、不做任何服务端渲染」的克制方向、以及 §3.2-6 的 ARM（鲲鹏 / 飞腾）部署目标
直接冲突。ARM 平台的原生转码若要做，单独计价。

已经是 Draco / KTX2 的送检件按原样透传，不做解压再压——二次编码是纯损失。
贴图体积超出第 2 节上限时，导入报告会给出中文处置建议（例如降低边长、改用 KTX2 重新导出），
**该建议由送检方在导出环节执行，我方不代为执行**。

## 2. 体量上限（导入时机械执行）

以下阈值由 `DEFAULT_POLICY` 逐项检查，超标当场在导入报告里逐项标出并给出处置建议。
**超标仍可导入**（不阻断工作），但其性能表现不作为验收依据。

| 指标 | 上限 | 接近上限（黄灯） | 来源 |
|---|---|---|---|
| 单文件大小 | **60 MB** | 48 MB | `[代码]` `DEFAULT_POLICY.maxBytes` · 指标 `bytes` |
| 三角面数 | **300,000** | 240,000 | `[代码]` `DEFAULT_POLICY.maxTriangles` · 指标 `tris` |
| 材质数量 | **60** | 48 | `[代码]` `DEFAULT_POLICY.maxMaterials` · 指标 `materials` |
| 贴图数量 | **40** | 32 | `[代码]` `DEFAULT_POLICY.maxTextures` · 指标 `textures` |
| 贴图解码后显存 | **128 MB** | 102 MB | `[代码]` `DEFAULT_POLICY.maxTextureBytes` · 指标 `textureBytes` |
| 单张贴图边长 | **2048 px** | 1638 px | `[代码]` `DEFAULT_POLICY.maxTextureSize` · 指标 `maxTextureSize` |
| 节点数量 | **5,000** | 4,000 | `[代码]` `DEFAULT_POLICY.maxNodes` · 指标 `nodes` |

黄灯阈值 = 上限 × **0.8**（`[代码]` `WARN_RATIO`）。

### v0.5 增补：独立贴图 / 环境贴图 / 媒体

模型之外，v0.5 起可以单独送检**贴图**、**环境贴图（HDRI）** 与**音视频**。它们各按自己的
一档评级，不与模型互评——一张 PNG 拿三角面数去量，报告里会出现「三角面数 0 / 300,000 通过」
这种正确但毫无意义的行，而这正是让人不再读报告的东西。

| 指标 | 上限 | 接近上限（黄灯） | 来源 |
|---|---|---|---|
| 图片文件大小（png / jpg / webp / ktx2） | **8 MB** | 6.4 MB | `[代码]` `DEFAULT_POLICY.maxImageBytes` · 指标 `imageBytes` |
| 环境贴图文件大小（.hdr） | **32 MB** | 25.6 MB | `[代码]` `DEFAULT_POLICY.maxHdriBytes` · 指标 `hdriBytes` |
| 音频文件大小（mp3 / wav / ogg） | **10 MB** | 8 MB | `[代码]` `DEFAULT_POLICY.maxAudioBytes` · 指标 `audioBytes` |
| 视频文件大小（mp4 / webm） | **50 MB** | 40 MB | `[代码]` `DEFAULT_POLICY.maxVideoBytes` · 指标 `videoBytes` |
| 图片最大边长（独立贴图 / 环境贴图） | **2048 px** | 1638 px | `[代码]` `DEFAULT_POLICY.maxTextureSize` · 指标 `imageSize` |

**格式是白名单，不是嗅探。** 能不能播由浏览器说了算，而在存完字节之后才发现播不了，
等于给了一个在库里看得见、永远听不到的资产。白名单：
`.png .jpg .jpeg .webp .ktx2 .hdr .mp3 .wav .ogg .mp4 .webm .glb .gltf`（`[代码]` `KIND_BY_EXTENSION`）。

**音频与视频那两条限的是等待，不是显存。** 一段讲解只被听一次，视频在热点面板里
播放、尺寸远小于原始分辨率——多出来的字节只会变成用户听到第一个字之前的等待。
超标时的处置建议也是照着这个写的（转 MP3 128kbps 单声道 / 压到 720p H.264 约 2 Mbps）。

**贴图的色彩空间不是送检项。** 基础色与自发光按 sRGB、法线/粗糙度/金属度/AO 按线性，
由运行时按槽位固定（MVP_V0 D3），送检方不需要也不能设置它——设错的症状是整个场景
偏色，而它会被可靠地误判成美术问题。

### v0.5 增补：一个文件可以对应多条媒体记录

同一段讲解用在两个步骤，就是**两条媒体记录、两个名字、一份字节**。导入时按内容哈希查重，
第二次导入命中缓存不重复存储，但照样新增一条记录。送检时不需要为此准备两份文件。

> **贴图那一行说的是解码后显存，不是文件大小。** 一张 2048×2048 的 PNG 可能只有 3 MB，
> 上传到 GPU 后占 16 MB（RGBA8）到 21 MB（含 mip 链）。耗尽显存的是后者。

|---|---|---|
| 每帧 draw call 上限 | `[待实测]` 当前经验值 1,200 | 导入体检统计的是材质数与网格数，不是绘制批次；真实上限取决于目标机器的 GPU 与驱动。**在目标机器跑过 benchmark 前，此数值不进合同。** |

## 3. 坐标系、单位与朝向

| 项 | 要求 | 来源 |
|---|---|---|
| 单位 | **米（m）**。若交付件为毫米或厘米，导入时声明源单位，系统按比例归一化 | `[代码]` `computeNormalization`，`UNIT_SCALE` |
| 上方向 | **Y 轴向上**。Z-up 的交付件（多数 CAD 默认）在导入时声明，系统绕 X 轴 −90° 校正 | `[代码]` `computeNormalization`，`axisRotated` |
| 原点 | 建议置于装配体的**几何中心或安装基准面**，不要留在远离模型的世界原点 | `[规范]` 无硬性要求，但原点远离模型会让「取景」把镜头拉得很远 |
| 变换 | 允许节点自带变换；不要求导出前 freeze | `[代码]` 实例化时逐节点保留 TRS |

> 归一化是**一次性**的：导入时把矩阵烘进根节点，此后文档里的坐标就是米、就是 Y-up。
> 同一份资产的第二次上传若声明了不同的源单位，会得到不同的比例——**同一批资产请统一声明。**

## 4. 命名与层级

这一节直接影响「二次上传后配置是否还在」，是全篇商务风险最高的一节。

| 项 | 要求 | 来源 |
|---|---|---|
| 对象名 | **1–120 字符**，不得为空 | `[代码]` `NodeSchema.name` 的 `min(1).max(120)` |
| 命名稳定性 | **同一部件在不同版本间必须保持同名同层级**。重命名或改变父子关系会导致该部件上的动画、热点、规则在二次上传后需要人工重新指定 | `[规范]` SCHEMA_SPEC §5.3 重映射阶梯：路径 → 名字 → 路径相似度 → 孤儿 |
| 同名兄弟 | **应避免**。glTF 允许同名兄弟，但重映射时会产生「多个同名候选」并要求人工选择 | `[代码]` `indexObjects` 首个命中优先并告警 |
| 空节点 | 无名、且子节点不超过一个的 Group 会被**折叠**，其变换并入子节点 | `[代码]` `isMeaningful` |
| 有意义的节点 | 网格、或有名字的节点、或有多个子节点的节点 | `[代码]` `isMeaningful` |

> **重映射阶梯的含义，用一句话说给商务侧：**
> 部件叫什么、挂在谁下面，决定了客户改一版模型之后，我们之前做的配置能不能自动跟过去。
> 名字全变 = 配置全部需要人工重指。这是可预防的返工，而预防手段就是这一节。

### KTX2 与色彩空间（v1.0 · T-219 实测）

送检件里的 KTX2 贴图我方能正确解码并**按用途设定色彩空间**：基础色 / 自发光按 sRGB，
法线 / 金属度 / 粗糙度 / 环境光遮蔽按线性。这一条要写进附件是因为它的失效方式很安静——
色彩空间搞错时模型仍然显示，只是偏灰或偏亮，看起来像「材质没调好」而不是「贴图读错了」。

**送检方需要注意的一条**：同一张 KTX2 被同时用作基础色与法线时，色彩空间只能按其中
一种设定。请为两种用途各导出一张。

**[v1.5]** 转码上线后，我方可代为把未压缩贴图转成 KTX2；届时本节增加「送检 / 处理后」
两栏的对照口径。v1.0 不做（见 §1「『允许』与『代做』的分界」）。

## 7. 性能验收前提

以下是我方承诺性能表现的**前提条件**。任一不满足，性能表现不作为验收依据：

1. 资产通过第 2 节的全部体量上限（导入报告全绿）；
   > **超标资产仍可导入**（不阻断工作），只是不进入性能验收范围——与技术方案 R01 同一口径
   > （2026-08-03 口径统一，产品拍板 P-13）。
2. 客户端浏览器**支持 WebGL 2**（Chrome 56+ / Edge 79+ / Firefox 51+ / Safari 15+）；
   > **v0 不支持 WebGL 1**，见 [ADR-0013](adr/0013-v0-不支持-webgl1.md)。这是必须在签约前
   > 与客户确认的一条：旧内核浏览器会看到一个说明页而不是内容。
3. 客户端**已启用硬件加速**且显卡驱动为近期版本；软件渲染下的表现不作为依据；
4. 验收在**目标机器**上进行，使用 [BENCHMARK.md](BENCHMARK.md) 描述的 benchmark 页面出具报告。

### v0.5 增补：灯光与阴影是独立的一档

benchmark 页从 v0.5 起会给出**两个**动态灯上限：无阴影的，和开 medium 阴影的。
它们经常差好几倍，而那个倍数正是排一个场景时最需要知道的数——
多一盏灯只是多一份逐像素着色（平滑上升），多一盏**投影**灯是多一整遍深度 pass（阶梯式上升）。

送检方需要知道的一条：**阴影质量三档对应 512 / 1024 / 2048 的阴影贴图**，
不是一个可以随便填的像素数（`[代码]` `shadowMapSizeFor`）。

**出厂默认是 `medium`（1024）。** 但送检方要知道另一件事：这个默认值**今天是拍的，不是测的**
——本仓库的开发与 CI 环境只有软件渲染，三档的真实代价量不到（[IMPL_NOTES](IMPL_NOTES.md) U-24）。
拿到目标机器之后按 IMPL_NOTES §2.5 的实验设计跑一遍，推荐档不是 `medium` 才会改，
**而改的只是出厂默认**：你已经交过来的文件里写着什么档，就还是什么档，迁移不碰它
（`shadow-quality-v2.json` 这份回归样本盯着这件事）。
