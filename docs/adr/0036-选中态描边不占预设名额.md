# ADR-0036 · 编辑器选中态描边是独立通道，不占那两个预设名额

- **状态**：Accepted
- **日期**：2026-08-05
- **任务卡**：T-241
- **相关**：[ADR-0021](0021-撤销-D20-v1.0-引入后处理链.md)（v1.0 引入后处理链）· D31 · 宪法 C3（一份引擎两个视图）· T-240（`MAX_ACTIVE_OUTLINE_PRESETS = 2`）

---

## 背景

T-240 定下「同一时刻最多两种描边预设，超限回落自发光」。T-241 要接的是**另一种**描边：
编辑器选中态。它的颜色来自 `meta.effects.outline.color`，而那个字段在 schema 里的注释
逐字写着 `Editor selection + the fallback` 与 `**Never overrides `highlight.preset`**`——
它不是 `HIGHLIGHT_PRESETS` 里的任何一项。

于是有一个规范没回答的问题：**两条 ECA 预设已经占满两条 pass 时，用户点选一个节点，
该建第三条 pass、抢占其中一条、还是不画？**

## 决策

**选中态是一条独立的 pass，不计入 `MAX_ACTIVE_OUTLINE_PRESETS`。**

清空的责任放在 **core 的 `setChromeVisible`**，不放在编辑器的 `useEffect` 里。

### 为什么不占名额

占名额意味着「我此刻选中了什么」会决定「我的规则高亮画成什么样」：选中一个对象，
第一种规则预设就掉进自发光回落。这个耦合有三重问题：

1. **用户解释不了**。两件事在心智上毫无关系，而症状是「我点了一下，另一个东西的颜色变了」。
2. **在播放器里无法复现**。播放器根本没有选中态，所以同一份文档在预览里回落、发布出去
   不回落——正是 C3 说的那种分叉，而且是最难查的那种（两边各自都"对"）。
3. **它把编辑期的操作变成了内容的一部分**。选中态是编辑期辅助物，与 grid / gizmo 同类。

### 为什么清空归 core

`setChromeVisible(false)`（进预览）已经是 grid / gizmo / 灯光辅助线的统一收口（T-235
的 `ChromeRegistry`）。选中态描边是同一类东西，走同一条路。

反过来——在编辑器的 `useEffect` 里判 `previewActive` 再决定推不推——会让**两处各记一半
状态**：预览中改选择、再退出预览时，谁也说不清该显示哪一批。而且那样一来
「进预览要清空」这条就只有 E2E 能观测，Node 单测碰不到（编辑器的那个 effect 不在 core）。

## 代价

1. **编辑器里最多同时三条 pass，而不是两条。** T-240 那条「三条 pass 在集显上直接掉帧」
   的论断因此在编辑器里被放宽了一档。⚠ **这个数字是拍的不是测的**——G0.5-8/H1 的目标机器
   benchmark 还没闭合（[ADR-0022](0022-G0.5-8-目标机器-benchmark-的挂载方式.md)），
   与「设备像素比封顶 / 剖切平面上限 / 描边预设上限」三个默认值同一处境。
2. 缓解它的是两条事实，都写进了测试：**进预览时那条 pass 一定不在**（`setChromeVisible`
   清空并 dispose），所以**出图与 parity 看到的仍然是至多两条**；而编辑期的帧率预算本来
   就宽于播放期（编辑器还挂着 gizmo、grid、灯光辅助线）。
3. **多一处「谁负责重推」的时序**：换策略（开关描边）与 chrome 重新可见时都要把选中集
   推一遍，漏任何一处的症状都是「选中的东西没有轮廓，而用户没有取消选择」。三处都有测试。

## 撤销条件

- H1 的目标机器实测显示：**编辑期三条 pass 在 M2（最低配）上跌破帧率门槛**，而两条不跌。
  那时把选中态改成占名额，并在超限时**优先保住选中态**（它是当前操作的直接反馈）。
- 或者出现第二种「不是预设、但要描边」的通道（例如剖切高亮）——那时「独立通道」这个
  说法会开始复制，应当改成一张有优先级的 pass 预算表，而不是每种通道各开一条。
