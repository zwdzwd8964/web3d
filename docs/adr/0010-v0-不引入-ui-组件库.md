# ADR-0010 · v0 编辑器不引入 UI 组件库

- 状态: Accepted（人工确认，2026-07-30）
- 日期: 2026-07-30
- 相关宪法条款: C6

## 背景

MVP_V0 §4 写"UI 组件：成熟组件库，不自研设计系统"，注明依据是技术方案 §5.1 补平工时缺口的
第 3 条。其意图是"不要把人日花在造按钮上"。

但 v0 编辑器的界面表面绝大部分是组件库并不提供的东西：层级树（虚拟滚动 + 拖拽改父）、
3D 视口、gizmo、属性网格（多选混合值）、规则编辑器（表单由动作 schema 生成）。
组件库能覆盖的只有按钮、输入框、下拉、对话框、标签页。

同时 C6 要求零外部运行时请求。多数组件库默认引用图标字体或 Google Fonts，
需要逐个排查并自托管，这本身也是成本。

## 选项

1. 引入整套（Mantine / Ant Design）—— 对话框与表单最省事；
   体积大、主题定制成本高，v1 做"主题与品牌换肤"（NORTH_STAR §3 v2）时会很难受；
   且需逐项核对许可证与外链资源。
2. 引入无样式 primitives（Radix UI）—— 可访问性与交互行为免费，样式完全自控；
   约 15 个包，且仍要写全部 CSS。
3. 不引。手写深色编辑器外壳，视觉语言沿用仓库里那份 `Web3D工具引擎_MVP原型.html`
   已经确定的配色与间距。原生 `<input>` / `<select>` / `<dialog>` 足以覆盖 v0 所需。

## 决定

选 3。§4 的意图是"别把人日花在造按钮上"，而 v0 真正要花人日的地方组件库都不覆盖；
手写约 200 行 CSS 不构成"自研设计系统"。

## 代价

- 可访问性要自己负责（焦点管理、键盘导航、ARIA）。原型里已有 `:focus-visible` 的处理，
  但对话框的焦点陷阱等需要补；
- 复杂交互控件（多级下拉、可拖拽排序列表）没有现成实现，v1 若功能面板暴涨会重新评估；
- 与 §4 字面不符。

## 撤销条件

若 v1 的功能面板数量超过 v0 的三倍，或甲方提出无障碍合规要求，
则引入 Radix primitives（选项 2）——它与现有手写样式可以共存，迁移是增量的，
不需要推倒重来。这是选 3 而非选 1 的关键理由：选 1 之后再想换回来是重写。
