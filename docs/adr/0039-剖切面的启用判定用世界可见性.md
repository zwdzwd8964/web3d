# ADR-0039 · 剖切面的「启用中」按世界可见性判定，I25 按自身 `visible`

- **状态**：Accepted
- **日期**：2026-08-05
- **任务卡**：T-243
- **相关**：X-03（剖切面是第四种承载体）· I25 / I27（`integrity.ts`，T-226 交付）· 宪法 C1（单一真源）

---

## 背景

剖切面的开关就是 `node.visible`——这是 X-03 让整个功能只花一个 core 文件的原因。
但「启用中」这件事有两个都说得通的判定：

| | 判据 | 今天写在哪 |
|---|---|---|
| A | 节点自己的 `visible` | `integrity.ts` 的 I25：`doc.nodes.filter(n => n.section !== null && n.visible)` |
| B | **世界可见性**：它自己以及每一个祖先都可见 | 本卡要实现的运行时 |

两者在一种情况下分叉：**剖切面的父节点被隐藏了。**

## 决策

**运行时用 B（世界可见性）。I25 保持 A 不动。**

### 为什么运行时必须是 B

用户收起一个分组之后，组里那把刀如果还在切，画面被剖开而**看得见的地方一个平面都没有**——
找不着，也关不掉。唯一的出路是把分组重新展开、找到那个节点、单独隐藏它。
这不是边界情况：把一堆辅助物收进一个分组是最常见的整理动作。

反过来，A 在运行时唯一的好处是「与 I25 一致」，而代价是一个用户无法自行退出的状态。

### 为什么 I25 不跟着改

`integrity.ts` 不在本卡的独占清单里，它是 T-226 已交付的验收面。而更重要的是：
**这两个函数回答的不是同一个问题。**

- I25 回答「你的文档里配了几把刀」——它是一条 `warn`，说的是「你写了 4 条，渲染器只吃 3 条」。
- 运行时回答「此刻要切几刀」。

分叉的方向也是安全的那一侧：父节点被隐藏时，I25 **多报**一条。一条 warn 多报的后果是
用户多看一眼；少报的后果是他配的第 4 条刀静默失效而没人提醒。

## 代价

1. **两处判据不同，而它们的名字听起来一样。** 有人照着 I25 的写法去改运行时（或反过来）
   就会踩空。缓解：两处都加了注释互相点名，本 ADR 是那两条注释的落点。
2. **I25 的提示在父节点隐藏时是错的**（说「4 条只取前 3」而渲染器只装了 3 条里的 2 条）。
   这是**已知的、如实登记的**不准确，登记在 IMPL_NOTES §3。
3. 世界可见性是一次向上走链的遍历。节点树深度在这个产品里是个位数，代价可忽略——
   但它是**每次 sync 每条平面各走一次**，如果将来平面上限从 3 提到几十，要重新看。

## 撤销条件

- I25 被某张卡改写成世界可见性（那时两处一致，本 ADR 作废）。
- 或者出现第三个「启用中的剖切面」判据（例如出图时要不要算上被隐藏的）——那时应当把
  判据提成一个 `@w3/schema` 的纯函数，让三处共用一份，而不是再写一条 ADR 解释三方分叉。
