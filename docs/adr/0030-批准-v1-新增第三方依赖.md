# ADR-0030 · 批准 v1 新增的五个第三方依赖

- 状态: **Accepted**（产品负责人 2026-08-03 拍板，拍板项 **P-15**）
- 日期: 2026-08-03
- 相关宪法条款: **C6**（零外部运行时依赖 · 断网构建）· **C2**（core 框架无关）· NORTH_STAR §5（「引入一个新的第三方依赖」必须留 ADR）· §7 指标表（Player 体积）· `CLAUDE.md` 停工条款第 3 条（规划里没列的第三方依赖必须停下来问人）

## 背景

`NORTH_STAR §5` 把「引入一个新的第三方依赖」列为**必须留 ADR** 的四类决定之一，`CLAUDE.md` 的停工条款第 3 条要求 agent 遇到规划外依赖时停下来问人。v1 的三级台阶合计需要五个新依赖，它们分散在十三份领域设计里，此前从未被集中审过一次。

集中审的理由不是流程洁癖，是**这五个包里有三个的批与不批，直接决定两条能力线做不做得成**：

- `TASK_BACKLOG_V1.md:698`（T-218）逐字写着：「**`draco3dgltf` 是规划外新依赖，须先批准**」。不批 → 造不出 Draco 压缩的 fixture → **G1.0-10「Draco 解码器在真浏览器里被同源加载」这条门槛没有被测对象**，v1.0 那条债（`IMPL_NOTES` 里 Draco 是「装了但没跑过」）就永远清不掉。
- `MVP_V1_进化规划.md:581` 把五个包列在一起，但归属写的是「v1.5 才有新依赖」——**这与 T-217 / T-218 两张 v1.0 的卡冲突**，那两张卡在 v1.0 就要用到其中两个。归属口径必须在本条里一次说清。
- 剩下两个（`fastify` / `pg`）是 `packages/server` 的技术选型，一旦落地就很难换。

**五个包能被批的核心理由是同一条**：它们**全部没有 node-gyp / prebuild / 系统库依赖**，跨架构是同一份产物。这条线不是修辞——它就是 `pnpm-workspace.yaml` 里 `sharp: false` 那个既有决定的延长线（注释原文：我们不在浏览器外跑原生步骤），也是 P-14 砍掉 KTX2 服务端转码（Khronos `ktx` 原生二进制 + amd64 单架构）的同一把尺子。**纯 WASM / 纯 JS 的进，需要编译的不进。**

## 选项

1. **逐个在各自的卡上临时批。**
   - 收益：不用现在决定。
   - 代价：T-218 会在 W1 波次卡住等一次审批，T-400 在 W25 再卡一次；而「审批」这件事的成本几乎全在**把五个包的架构影响想清楚**，分五次想不会更便宜，只会更不一致。且 `CLAUDE.md` 停工条款第 3 条会在五个不同的时点各触发一次停工。

2. **一次全批（本条）。**
   - 收益 / 代价见「决定」与「代价」。

3. **全不批，绕过去。**
   - 收益：依赖数不变。
   - 代价：Draco fixture 只能手工二进制拼装或从外网下一份现成件——前者是不可维护的，后者违 C6 且来源不可审计；`packages/server` 只能手写 HTTP 框架与 PostgreSQL 协议，那是把 v1.5 的预算翻倍去省五个成熟包。**这个选项登记在此，是为了让后人不必重开它。**

## 决定

**五个全批。产品负责人 2026-08-03 拍板（P-15）。**

> **批准 ≠ 安装。** 见下方「落地纪律」：本条只解除审批闸门，每个包在**它自己的引入卡开工那天**才写进 `package.json` 与 lockfile。这一条是本 ADR 与一次普通「全批」之间的全部差别。

### 逐个登记

#### 1 · `draco3dgltf`

| 项 | 内容 |
|---|---|
| **用途** | Draco 几何**编码**。v1.0：`scripts/gen-draco-fixture.mjs` 一次性离线生成 `e2e/fixtures/pump-draco.glb`（`buildSamplePumpGlb()` → Draco 压缩 → 写 fixture，产物提交进仓库）。v1.5：服务端转码作业里的 Draco 编码 |
| **许可证** | **Apache-2.0**（Google Draco）。允许商用与私有化再分发，**要求随分发附 NOTICE** |
| **形态与架构无关性** | emscripten 产物：**WASM + JS 胶水**，无 node-gyp、无 prebuild、无系统库。amd64 / arm64 同一份产物，不撞 v3 的 ARM 与信创目标 |
| **体积影响** | **Player bundle 0 KB。** v1.0 侧是 `devDependency`，只在人工执行 fixture 生成脚本时用到，**不在任何 build / CI / verify 路径上**；v1.5 侧只进服务端。浏览器里的 Draco **解码**走的是已自托管在 `vendor/` 的 decoder（铁律 7），与本包无关 |
| **引入卡** | **T-218**（v1.0，devDep + 该卡独占 `packages/core/package.json`）· **T-420**（v1.5，服务端转码作业） |

#### 2 · `meshoptimizer`

| 项 | 内容 |
|---|---|
| **用途** | 提供 `MeshoptSimplifier`，注入给 `@gltf-transform/functions` 的 `simplify()` 算子——即「上传即转码」里**可选减面**那一档（边界与理由见 [ADR-0031](0031-减面移出-Out-of-Scope.md)）。**默认关闭**（v1 规划 §1.3「减面默认档位」） |
| **许可证** | **MIT** |
| **形态与架构无关性** | npm 包发的是 **WASM（base64 内嵌）+ JS API**，无原生构建步骤。跨架构同一份产物 |
| **体积影响** | **Player bundle 0 KB**，只进服务端转码链 |
| **引入卡** | **T-420 / T-422**（v1.5）。**批准批次归 v1.0（与另两个同批一次审完），第一个消费者在 v1.5** |
| ⚠ **边界** | **引入本包不等于支持 `EXT_meshopt_compression` 的输入。** v1 规划 §1.3 已裁死：`meshopt` 压缩的**送检件拒收**，`unsupportedExtensions` 报 fail（附件A §1 只允许 Draco，且 `GLTFLoader` 没接 `setMeshoptDecoder`）。**我们用它做简化，不用它做解码**——两件事混在一起，附件A 的口径当场就破 |

#### 3 · `@gltf-transform/extensions`

| 项 | 内容 |
|---|---|
| **用途** | `registerExtensions(ALL_EXTENSIONS)`，让 `readGlb` 认识 Draco / meshopt 等 glTF 扩展，使 `auditGlb` 对声明 Draco 的 GLB **不再抛异常**（T-217）；生成 Draco fixture 时注册 `KHR_draco_mesh_compression`（T-218） |
| **许可证** | **MIT** |
| **形态与架构无关性** | **纯 JS**，零 WASM、零原生。架构无关是平凡成立的 |
| **体积影响** | **零新增下载**——它今天已经作为 `@gltf-transform/functions`（`packages/editor/package.json:18`）的传递依赖躺在 lockfile 里，本条只是把它**提升为直接依赖**。落点在体检 / 导入路径（`packages/core/src/assets/audit.ts`），`pnpm size` 的实测由 **T-217** 当卡回填；若实测使 Player gzip 逼近 400 KB，按 [ADR-0021](0021-撤销-D20-v1.0-引入后处理链.md) 的撤销条件停下来重评，**不许当场调预算** |
| **引入卡** | **T-217**（v1.0）· **T-218**（v1.0） |
| ⚠ **注意** | 提升为直接依赖意味着它的升级不再跟着 `@gltf-transform/functions` 走。**四个 `@gltf-transform/*` 包的版本号必须完全一致**（今天全仓是 `4.4.2`），不一致时它们内部的 `Property` 注册表会出现两份，症状是运行时「扩展没被识别」而**不是编译错误**——最难查的那一类 |

#### 4 · `fastify`

| 项 | 内容 |
|---|---|
| **用途** | `packages/server` 的 HTTP 骨架：可注入 db / objectStore 的 `createApp()`、路由生命周期、`preHandler` 统一鉴权钩子（权限查表在 `preHandler`，**不下沉到 repo 层**） |
| **许可证** | **MIT** |
| **形态与架构无关性** | **纯 JS**，无原生依赖。amd64 / arm64 同一份镜像层 |
| **体积影响** | **前端 0 KB。** 服务端镜像与离线 tar 的体积按 npm 解包体积上升，计入 T-419 的三容器部署形态 |
| **引入卡** | **T-400**（v1.5，`@w3/server` 包骨架）；`preHandler` 鉴权在 **T-404** |

#### 5 · `pg`

| 项 | 内容 |
|---|---|
| **用途** | `packages/server/src/repo/pg.ts` 的 PostgreSQL 方言实现。另一侧方言是 Node 内置的 `node:sqlite`，零依赖；同一套 repo 单测在两个方言上各跑一遍 |
| **许可证** | **MIT**（node-postgres） |
| **形态与架构无关性** | `pg` 本体是**纯 JS** 实现的 wire protocol 客户端，无原生代码 |
| **体积影响** | **前端 0 KB**，只进服务端 |
| **引入卡** | **T-401**（v1.5，SQL 方言层 + 迁移运行器） |
| ⚠ **硬约束** | **不许安装 `pg-native`。** 它需要系统 `libpq` + node-gyp，会把服务端镜像绑死到构建架构，同时撞 v3 的 ARM/信创目标与 C6 的断网构建。这条不是建议，是本条批准的前提；`pg-native` 出现在任何一份 lockfile 里，即视为本 ADR 被违反 |

### 落地纪律（本条的执行部分）

1. **批准与安装是两件事。** v1.0 只把 v1.0 真正会 import 的两个（`draco3dgltf` · `@gltf-transform/extensions`）写进 `package.json`；`meshoptimizer` / `fastify` / `pg` 在本条获批，但**到各自的引入卡（T-420 / T-400 / T-401）开工那天才落进 lockfile**。
   理由是本仓库刚犯过一次同形错误：`@gltf-transform/functions` **在 `package.json` 里躺了一个版本周期、零 import**，lint 与审计都没抓到（v1 规划 §3.1 已把它登记为「一条假依赖，一并清」）。**提前安装一个没人 import 的包，制造的正是那种依赖。**
2. **五条许可证登记进 `docs/LICENSES_LIBRARY.md`**（该文件已在 **T-218** 的独占清单里），新增一节「三方 npm 依赖」，逐条写：包名 / 版本 / 许可证 / 用途 / 引入卡 / **是否随分发再分发**。`draco3dgltf` 的 Apache-2.0 NOTICE 义务在这一节点名。
3. **版本一律精确锁定**（仓库既有的 `saveExact: true`），不许 caret。这条今天有一处已知违反：`@playwright/test` 是全仓唯一带 caret 的依赖，由 **T-208** 收口。
4. **断网 CI job `offline`（G1.0-9）的预热 store 必须同批更新。** 每加一个包就多一个「忘了预热」的失败模式；预热遗漏的表现是**安装步骤红**，不是编译步骤红，别去查错地方。

## 代价

明确接受六条：

1. **依赖数增加，断网构建与离线镜像的预下载面同步变大。** `pnpm install --offline --frozen-lockfile`（G1.0-9 的 `offline` job）的预热 store 每多一个包就多一次可能的遗漏；离线 tar 的体积与制作时间同步上升，而离线 tar 正是 v3 私有化交付的主形态。**C6 的成本从来不在"不引 CDN"，在"每一个依赖都得能离线装上"。**
2. **`draco3dgltf` 与 `meshoptimizer` 的 WASM 是不可审计的字节。** 我们看不进去，code review 也发现不了它变了。唯一防线是精确版本 + lockfile 的完整性哈希——**这是一条真实的信任转移，不是形式主义地写在这里**。
3. **许可证清单从"人记得"变成"必须维护"。** 五条新条目，其中 Apache-2.0 的 NOTICE 义务是分发时才会被追问的那一类；它不会在任何一次 CI 里失败。
4. **`@gltf-transform/extensions` 从传递依赖提升为直接依赖，版本漂移的责任转到我们身上。** 四个 `@gltf-transform/*` 包必须同版本，而没有任何机制强制这一点——症状还是运行时的，不是编译期的。
5. **`fastify` / `pg` 把服务端技术选型定死。** v3 的国产数据库适配（达梦 / 人大金仓）**必须走 T-401 的方言层，而不是换掉 `pg`**；但方言层今天只在 `pg` 与 `node:sqlite` 两个方言上被验证过，**两个都不是达梦**。也就是说 v3 的关键假设在 v1.5 结束时仍然是一个未被检验的假设。
6. **五个里有三个在 v1.0 期间一行代码都用不到。** 「落地纪律」第 1 条把这个代价压到了最低（获批但不安装），但没有消除它：**一个被批准了却迟迟不安装的依赖，会在 v1.5 开工时被当成"早就说好了"而跳过重新评估**。重新评估的触发点写在下面的撤销条件里。

## 撤销条件

- **任何一个包在某次升级中引入 node-gyp / prebuild / 系统库依赖** → 立即钉死在上一个纯 JS/WASM 版本，并写一条新 ADR 重评。**不许"先装上再说"**——那会在 v3 的 ARM 镜像上以构建失败的形式暴露，而那时已经隔了两级台阶，没人记得是哪次升级带进来的。
- **`pg-native` 出现在任何一份 lockfile 里** → 视为本条被违反，回滚该次变更。
- **Player gzip 因 `@gltf-transform/extensions` 而使实测总增量突破 350 KB** → 按 [ADR-0021](0021-撤销-D20-v1.0-引入后处理链.md) 的同名判据停下来重评 400 KB 口径，**不许当场调预算**；处置候选是把体检路径的扩展注册改成按需动态 import。
- **「上传即转码」的 Draco 那半边也被砍掉**（KTX2 已由 P-14 砍掉，见 [ADR-0031](0031-减面移出-Out-of-Scope.md)）→ `draco3dgltf` 只剩 fixture 生成这一个 devDep 用途，服务端用途消失，应把它从 `packages/server` 的依赖里移除而不是留着。
- **减面被证明没人开**（默认关闭且用户从不打开）→ `meshoptimizer` 失去唯一消费者，**应当移除**，而不是留在 lockfile 里等下一个用途。留下来它就是第 6 条代价的实例化。
- **断网 job `offline` 因为某个新依赖的预热遗漏红过两次以上** → 说明预下载面已经超出人工维护能力，停下来把依赖清单自动化，而不是继续手工补 store。
- **本条获批的某个包到它的引入卡开工时仍未被 import** → 说明当初的用途判断错了，此时**不许因为"已经批过"而顺手装上**，应回到本条重新评估该包是否还需要。
