# ADR-0021 · 撤销 D20：v1.0 引入后处理链（描边），Player 体积口径维持 400 KB

- 状态: Accepted
- 日期: 2026-08-03
- 相关宪法条款: C6（零外部运行时依赖，本条不破）· C3 · NORTH_STAR §3（v1 晋级门槛第四条 `:152`）· §7 指标表（`:274`）· §4 分诊 Q4
- Supersedes: `MVP_V0_5_进化规划.md:416-422` 的 D20

## 背景

D20 明令 v0.5 不引后处理，原文两条理由：

> 「`EffectComposer` / `postprocessing` 不进依赖树。……R07（后处理×透明×抗锯齿三角冲突）继续整体推迟到 v1 一次性解决。」
> 「❌ 错误：『顺手加个 Bloom 让金属好看点』——引入 R07 的全部复杂度，且 player 体积余量（170 KB）会被吃掉一大块。」

两条理由今天的状态：

- **第一条到期了。** R07 的处置是 v1 晋级门槛的第四条（`NORTH_STAR.md:152`：「出图 + 后处理 + 透明背景的三角冲突有明确处理策略并有回归用例」）。D20 说的「推迟到 v1 一次性解决」，现在就是那个 v1。
- **第二条被实测推翻了。** three 自带 `examples/jsm` 的 `EffectComposer + OutlinePass + OutputPass` 一组九个文件，源文件 gzip 10.54 KB，**去注释后 6.20 KB**（`design/postfx.md:39` 选型表 A 行、`:522` 体积明细）。v1 全部领域的实测加总增量是 **+59.3 KB**，从当前 243.8 KB 走到 **≈303 KB**，预算 400 KB 仍有约 97 KB 余量。「吃掉一大块」在 6.20 KB 这个数字面前不成立。

推动撤销的功能理由只有一个，但它是硬的：**被遮挡零件的轮廓**。v0 的高亮是 emissive，emissive 画在物体自己的像素上，零件被壳体挡住时一个像素都看不见。而拆装教学的头号动作恰恰是「先高亮它在哪，再拆开给你看」——顺序反了就没有教学价值。透视轮廓非后处理不可。

## 选项

1. **继续不引，描边用反向外壳（backface hull）。**
   - 收益：不触分诊 Q4，保住「唯一渲染出口」纪律；体积增量接近 0。
   - 代价：放弃透视轮廓（被遮挡零件仍然看不见轮廓，即上面那条唯一的功能理由落空）；硬边处会裂；R07 门槛第四条过不了——外壳法根本不进入 R07 的问题域，等于用「不做」回答一条门槛。

2. **引 three examples 的 `EffectComposer + OutlinePass + OutputPass`（本条）。**
   - 收益：零新增第三方依赖（three 已在依赖树里，且仓库已有四处 `examples/jsm` 深导入先例）；去注释 gzip 实测 6.20 KB；`OutlinePass` 原生支持 `hiddenEdgeColor`，透视轮廓是它的出厂能力。
   - 代价：见「代价」。

3. **引 pmndrs `postprocessing`。**
   - 收益：自带 SMAA 与一整套 effect 体系。
   - 代价：新增第三方运行时依赖，社区量级 40–60 KB gzip（未安装，无法实测），断网安装要重新验证，撞 C6 与「零新增依赖」纪律。为一个只要描边的需求引一整套框架，是分诊 Q2 被当成 Q4 做。

## 决定

选 2，并在本条里**逐项回答 R07 的三条腿**。

### 腿 1 · 抗锯齿：MSAA 原地保住，SMAA 与 FXAA 都不引

技术方案 R07 写的缓解是「补 SMAA/FXAA」。**这条在 three 0.185 上已经过时。** 做法是不使用 `EffectComposer` 的默认 target，自己造一个：

```ts
const rt1 = new WebGLRenderTarget(width, height, { type: HalfFloatType, samples: 4 })
const composer = new EffectComposer(renderer, rt1)
// rt2 只被全屏四边形写，多重采样对它毫无收益，却要多付一份 4× 的 renderbuffer。
// EffectComposer 的构造是 rt1.clone()，而 clone 会连 samples 一起复制（RenderTarget.js:383）。
composer.renderTarget2.dispose()
composer.renderTarget2 = new WebGLRenderTarget(width, height, { type: HalfFloatType, samples: 0 })
```

机制证据：`three/src/core/RenderTarget.js:63`（默认 `samples: 0`）、`:194`、`:383`；`WebGLTextures.js:2104`（`samples > 0` 时建多重采样 framebuffer）、`:2278`（blit 解析）；`WebGLRenderer.js:2979-2981`。**体积代价 0 KB，观感与今天的 `antialias: true` 同档。**

- **不引 SMAA**：单文件去注释后仍 **42.79 KB** gzip（`postfx.md:41`），占 400 KB 预算的 10.7%，且其中两张 base64 查找图不可压缩（`grep -c 'data:image'` = 2）。R07 原文把「补 SMAA/FXAA」并列写，是把两个相差 15 倍的东西当成同一件事。
- **不引 FXAA**：只要 2.3 KB，但边缘偏软、细线闪烁——而 MSAA 根本不需要放弃，没有理由降档。
- **降级路径**：WebGL2 里 `RGBA16F` 作可渲染的多重采样附件依赖 `EXT_color_buffer_float`。缺这个扩展时（老集显 / 部分虚拟机）退到 `{ type: UnsignedByteType, samples: 4 }`，代价是色调映射前少了 HDR 余量、亮部会有带状。**必须 warn 一行中文日志，不许静默。** 检测挂在 `capability.ts:19-33` 已有的三档判定同一处。

### 腿 2 · 透明背景：**降级**，不是拒绝

先把机制说清楚，因为「边缘发灰」这个词掩盖了真实原因：

- 我们的渲染器 `alpha: true` 是无条件的（`scene-runtime.ts:359`），`WebGLBackground.js:22` 因此把 `clearAlpha` 置 0，**composer 的 target 也是 RGBA，透明背景本身没问题**。
- 问题在 `OutlinePass._getOverlayMaterial()` 末尾的 `blending: AdditiveBlending`。three 对**非预乘** additive 用 `gl.blendFuncSeparate(SRC_ALPHA, ONE, ONE, ONE)`（`WebGLState.js:679`）。描边落在背景像素上时，RGB 按 `src.rgb * src.a` 加进去、alpha 按 `src.a` 加进去——**轮廓外扩那半圈得到 RGB > A**。存成非预乘 PNG 再合成，就是「边缘发亮 / 发灰」的确切来源。

**裁决：透明背景导出时强制走 `direct` 模式，导出的 PNG 不含描边，导出面板给一句中文提示「透明背景导出不包含描边效果」。** 可机械断言（导出路径断言 `pipelineMode === 'direct'`），且不需要 fork `OutlinePass` 的 shader。雾不受影响——雾画在物体像素上，背景像素仍是 alpha 0。

**这一条覆盖 `design/render-out.md` ADR-C 的「拒绝导出」主张**（`render-out.md:166` 的 `planCapture` 第 4 条、`:1095`）：两份设计在同一处给出了相反的处置，此处裁为**降级**。理由——拒绝会让用户在验收现场拿不到图，而他真正要的是一张能贴进 PPT 的透明底图；描边可以没有，图不能没有。`planCapture` 的第 4 条相应从 `reject` 改为「降档 + `notice`」，单测断言从「返回 reason」改为「返回 `pipelineMode: 'direct'` 且 `notice` 含该中文句」。

### 腿 3 · 超分辨率：倍率按管线模式钳制

`OutlinePass` 在分辨率 (W,H)、`downSampleRatio = 2` 下分配 7 个 target（`OutlinePass.js:156-190`）≈ **19·W·H** 字节；composer 侧（rt1 samples 4 + 解析纹理 + rt2 samples 0）≈ **48·W·H** 字节。实测表（`postfx.md:129`）：

| 导出尺寸 | direct | composed（1 个 OutlinePass） | composed（2 个） |
|---|---|---|---|
| 1920×1080 | ~0 额外 | ~139 MB | ~178 MB |
| 3840×2160（2×） | ~0 额外 | ~555 MB | ~712 MB |
| 7680×4320（4×） | ~0 额外 | **~2.2 GB** | ~2.8 GB |

**裁决：`composed` 模式下导出倍率上限 2×，`direct` 模式下 4×。** 导出前用上表的公式做一次预估，超阈值直接给中文提示并降档，不许让浏览器丢上下文——丢上下文的现象是「整个页面变白」，用户无法把它与「导出失败」联系起来。公式写进代码注释，不靠上下文记忆。

### 第四条 · 体积口径：维持 400 KB，并把 v1 那格从 600 下调为 400

实测加总增量 +59.3 KB → ≈303 KB，不超 400。因此：

- **维持 400 KB 不变**；
- 把 `NORTH_STAR.md:274` 指标表里 v1 那格的 `≤ 600 KB` **下调为 `≤ 400 KB`**。理由一句话：**预算是用来约束的，不是用来花的。** 一个从未被逼近过的 400 KB，没有理由因为「v1 更大」就先放宽 200 KB；真需要时再写 ADR 抬，代价是一条 ADR，收益是余量始终是余量。
- 附带订正一处**按字面执行会命令不存在**的门槛：`NORTH_STAR.md:139` 的 G0.5-7 写 `pnpm size-limit`，而 `package.json:27` 里实际的脚本名是 `size`（`"size": "node scripts/check-size-budget.mjs"`），`verify`（`:23`）串的也是 `pnpm size`。四份文档统一改成 `pnpm size`。`scripts/check-size-budget.mjs:34` 的 `budgetBytes: 400 * 1024` 因本条**不需要改**。

### 第五条 · composer 只在开启描边时构造

`meta.effects.outline` 新增 `enabled: boolean.default(false)`（schema v3 冻结裁决 X-02）。`enabled === false` 时**根本不构造 composer**，老文档走的还是今天那行 `renderer.render()`。于是 G0.5-6「老文档默认观感逐参数不变」原样继承到 v1.0，且它是**可机械断言**的（断言 composer 工厂被调用 0 次），不是承诺的。

这条同时裁掉 `design/schema-v3.md §16 Q2` 的相反主张（「Outline 全量替换 emissive、不加开关」）：不加开关意味着所有历史文档的高亮观感在升级当天全变，而 G0.5-6 是一条已经交付的承诺。**变异检验**：把 `enabled` 的默认值改成 `true`，「老文档不构造 composer」那条断言必须转红；改不红的断言不算数（E18 教训）。

## 代价

明确接受八条：

1. **渲染路径从一条变两条**（`direct` / `composed`），测试面积翻倍；`emissive` 与 `outline` 两套高亮实现永久共存，任何一次高亮相关的改动都要在两条路径上各验一遍。
2. **composed 模式的渲染成本明显上升**：1080p 下多约 139 MB 显存与数趟全屏 pass。弱机档位只能由目标机器实测定档，而那次实测的挂载方式尚未拍板（ADR-0022）——**在它闭合之前，composed 的默认档位是拍的，不是测的**。
3. **透明背景导出永远不含描边；4× 与描边互斥。** 用户勾了描边却得到一张没有描边的图，靠一句中文提示弥补，仍然是所见非所得。
4. **深导入 `three/examples/jsm` 的九个文件，脱离 three 的 semver 保护面。** examples 目录不承诺 API 稳定，每次升 three 都要重新核对这九个文件——这条成本是永久的，不是一次性的。
5. **分诊 Q4 被触发一次。** 这是 ADR-0018 之后第二次对渲染路径做结构性改动。按 `NORTH_STAR §4`，Q4 需要重新评估预算与工期，本 ADR 就是那次评估的记录。
6. **400 KB 不上调意味着后面三条线的余量只剩 ≈97 KB。** v1.2 的 flows/pages、v1.5 的分享与多场景，体积必须逐卡预估、逐卡回填 METRICS，不能事后再说。这是自找的约束，接受它是因为「先放宽再说」在体积这件事上从来只有一个方向。
7. **`OutlinePass.pulsePeriod` 必须硬编码为 0** 并配一条断言：它非 0 时内部会调 `Math.cos(performance.now() …)`，虽然不在 `packages/core/src/eca/` 目录下（铁律 6 管的是 ECA），但真实时间会让 E2E 的像素断言不确定。这是一条**语言层面挡不住、只能靠人记住**的约束，写在这里是它唯一的存档。
8. **R07 从「一条待办」变成「三条永久约束」**：samples:4 的 target、透明降级、倍率钳制，三条都要有回归用例并永久维护。门槛过了不等于问题消失了。

## 撤销条件

- **目标机器实测显示 `composed` 模式在客户最低配机器上帧率不可接受** → 退回反向外壳方案（选项 1），并**公开放弃「被遮挡零件的轮廓」**这一能力。不许留成「以后再说」——那样会得到一个既有 composer 又没人敢开的死代码。
- R07 三条腿里**任何一条给不出回归用例** → 晋级门槛第四条过不了，本 ADR 作废，D20 复效。
- 目标机器缺 `EXT_color_buffer_float` 的比例不可忽略，或 8-bit 降级的带状被客户判为不可接受 → 改用 FXAA（**不是 SMAA**，除非体积预算已抬到 600 KB——而本 ADR 明确拒绝抬）。
- 实测总增量突破 350 KB → 停下来重新评估 400 KB 口径，走一条新 ADR，**不许当场调预算**。
- `three/examples/jsm` 的这九个文件在某次 three 升级中出现破坏性变更且无平滑迁移路径 → 重新评估选项 3（pmndrs），此时体积预算的讨论一并重开。
