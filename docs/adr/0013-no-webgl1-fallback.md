# ADR-0013 · v0 不支持 WebGL1，降级改为能力检测与阻断页

- **状态**：已接受
- **日期**：2026-07-31
- **相关**：T-111 · 技术方案「国产浏览器内核偏旧」· 宪法 C6（断网能跑）

---

## 背景

T-111 卡片要求：

> 检测 WebGL2 → 不可用则降级 WebGL1 + 关闭不兼容特性 + 页面顶部提示。
> **降级路径必须能跑通黄金路径**（国产浏览器内核偏旧）

这条要求的出发点是对的：目标客户可能部署在基于旧 Chromium 内核的国产浏览器上，
拿不到 WebGL2 就是白屏。

但它用当前锁定的依赖**无法实现**，这是一个技术事实，不是取舍：

| 事实 | 核对方式 |
|---|---|
| three 0.185 的构建产物里没有 `WebGL1Renderer` | `grep WebGL1Renderer node_modules/.../three.module.js` → 零命中 |
| `WebGLRenderer` 只请求 `webgl2` 上下文 | 同文件里 `webgl2` 出现 1 次，`'webgl'` / `experimental-webgl` 零命中 |

three 在 r155 弃用、r163 删除了 WebGL1 支持。MVP 规划 §4 把 three 锁在 0.185，
理由是「three 的次版本带破坏性变更」。

## 决策

**v0 不支持 WebGL1。** T-111 改为实现 `packages/core/src/runtime/capability.ts`：

1. 渲染任何东西之前先探测，用一次性 canvas，探完立刻 `loseContext` 释放；
2. 区分三种情况并给不同建议——它们的解法完全不同：
   - 完全没有 WebGL → 建议开启硬件加速 / 升级驱动
   - 只有 WebGL1 → 建议升级浏览器，并**明确说出**需要 WebGL 2
   - 有 WebGL2 但是软件渲染 → 说明会卡顿，允许「仍然继续」
3. 失败时渲染一个中文阻断页（纯 DOM + 内联样式，不依赖任何样式表——
   失败可能发生在应用做的第一件事上）。

T-111 卡片**保持未勾选**：交付的不是卡片要求的东西。

## 代价

- **旧内核客户用不了。** 只有 WebGL1 的浏览器会看到一个说明页而不是内容。
  这是真实的商业损失，不是技术细节，必须让商务侧知道。
- 「降级路径跑通黄金路径」这条验收线**无法执行**，因此 v0 不能声称支持旧内核。
- 阻断页本身没有自动化验收（需要一个没有 WebGL2 的浏览器才能真跑），
  只有单测覆盖判定逻辑。

## 撤销条件

出现以下任一情况，重新评估：

1. **实际部署环境里出现了没有 WebGL2 的浏览器**——这是最可能的触发条件。
   届时选项有二：把 three 回退到 0.162 一带（要重跑全部 core 测试与 E2E，
   `TransformControls` 与加载器 API 都变过，vendor 解码器要重同步），
   或者为旧内核单独出一个降级构建。两者都是可观的工作量，应当先摸清环境再决定。
2. three 恢复 WebGL1 支持（可能性极低）。
3. 客户合同里写明了必须支持某个具体的旧内核版本。

## 未采纳的方案

| 方案 | 不采纳的理由 |
|---|---|
| 回退 three 到 0.162 | 违反版本锁定；要重跑并可能重写 374 条 core 测试与 9 步 E2E；`TransformControls` 在 0.185 已从 Object3D 改为 Controls，gizmo 要改回去；**在还没有证据表明客户环境真的需要它之前，这个代价买不到任何东西** |
| 自己写 WebGL1 兼容层 | 不存在成熟方案；等于在 v0 里维护一个渲染后端 |
| 沉默降级到不渲染 | 就是现在要修的那个白屏 |
