# ADR-0022 · G0.5-8 目标机器 benchmark 的挂载方式

- 状态: **Accepted**（产品负责人 2026-08-03 拍板选项 2）
- 日期: 2026-08-03 起草 · **2026-08-03 拍板（产品负责人 P-2）**
- 相关宪法条款: NORTH_STAR §3（版本阶梯与晋级门槛 `:91` / `:140`）· §8（破例的唯一合法路径 `:283-292`）

> ✅ **已拍板（2026-08-03，产品负责人，拍板项 P-2）**：选**选项 2** —— G0.5-8 从「v0.5 晋级 v1 的**入口**门槛」改挂为 **v1.0 的出口门槛**，v1.0 立即开工。逐字表述见下方「决定」栏。
> 起草时那句「本 ADR 把两个选项的代价写全，**不做选择**」到此作废。**两个选项的原文一字不删**——被否掉的那一条的代价，是将来重开这场讨论时唯一的对照面。

## 背景

**这是一个合规问题，不是一个技术问题。**

宪法白纸黑字写着门槛不过不许开工下一级：

> `NORTH_STAR.md:91`：「**每一级有一个『晋级门槛』，门槛不过不许开工下一级**——这是防止底座被功能进度挤压的唯一机械手段。」
> `TASK_BACKLOG_V0_5.md:913-915`：「**七条机械门槛全过，第八条卡在硬件供给上。** 按 NORTH_STAR §3 的原文『任何一条不过，不许开工 v1』——所以现在**不能开工 v1**，需要的是一台目标机器，不是更多代码。」

未过的那一条是 G0.5-8（`NORTH_STAR.md:140`）：目标机器 benchmark 实测（含灯光/阴影档位）。它缺的不是代码，是一台带真实 GPU 的机器——本仓库开发环境与 CI 都只有 SwiftShader 软件渲染，`docs/BENCHMARK.md` 的「当前状态」一节自己写着「**尚无目标机器实测数据**……**不可作为验收依据**」，帧率类 / 灯光档 / 阴影档三行全是「未记录数字」。

它已经被顺延过一次：v0 的 G0-7 经 ADR-0015 顺延为 v0.5 的 G0.5-8，当时的原话是「v0.5 晋级 v1 前必须补上这次实测」。现在是那个「晋级 v1 前」。

因此：**v1 的每一行代码都写在一个未被授权的开工状态里。** 这句话必须原样写进这份 ADR，因为它是本条存在的全部理由。

还有一层不能忽略的连带影响：**至少三份领域设计的关键默认值都在等这台机器的数字**——

| 默认值 | 在等什么 | 出处 |
|---|---|---|
| 像素比封顶（`devicePixelRatio` 的上限） | 高 DPI 机器上描边的实际填充率 | `design/postfx.md`（v1.0 的像素比封顶卡） |
| 剖切平面数量上限 | 多平面剖切在目标机器上的帧时间 | `design/explode-clip.md` |
| 描边预设上限（composed 档位） | `composed` 模式在最低配上的帧率 | ADR-0021 腿 3 与 `postfx.md:129` 的显存表 |

不做实测，这三个默认值只能**先拍后改**。而「先拍后改」在 v0.5 的 M8 已经付过一次代价：8 个默认值被改坏，而全套测试全绿。

## 选项

### 选项 1 · 先跑再开工：现在安排一台目标机器，闭合 G0.5-8，然后开工 v1.0

- **收益**
  - 宪法零例外，门槛制度在第一次被真正挑战时守住了。这是它作为「唯一机械手段」的价值所在。
  - 三个关键默认值有真数字，不是拍的。
  - 性能承诺在写第一行 v1 代码之前就成立；若实测很差，代价是重新规划 v1 范围，而不是重做一个已实现的 v1.0。
- **代价**
  - **v1 开工推迟到机器到位那天，推迟原因与代码质量无关。** 这是一个纯外部依赖，项目侧做任何事都不能缩短它——ADR-0015 当初拒绝这条路，用的正是这个理由。
  - 人工成本约 **0.5 人日**（跑三档、抄数、回填），但代码侧的准备（三档机器操作手册 / 报告 JSON 格式 / 回填脚本 / `--check` 模式）**仍然要先做**，它是这 0.5 人日成立的前提。也就是说选项 1 并不省掉选项 2 的那部分工作量。
  - **若机器迟迟不到，整个 v1 无限期停摆**，而停摆期间没有任何替代产出——这正是 v0.5 被插入时想避免的空转。

### 选项 2 · 重新挂载：把 G0.5-8 挂为 v1.0 的**出口**验收项（规划 §7.2 的人工项 **H1**）

走 `NORTH_STAR §8` 破例四步：写 ADR / 说明代价 / 写撤销条件 / 带过期版本号（`v1.0`）。同时交付使它「拿到机器后 0.5 天可闭合」的全部代码：三档机器操作手册、报告 JSON schema、`scripts/apply-bench-report.mjs` 回填脚本与 `--check` 模式、三份报告入库的门槛判据。

- **收益**
  - v1 立即开工；破例是**显式的、有到期版本号的**，不是默默的。§8 的四步全部走完，制度没有被绕过，只是被使用了。
  - 门槛没有被删掉，只是换了挂载点：v1.0 出口仍然拦得住 v1.2。
- **代价**
  - **v1.0 的全部开发都在「性能承诺尚未成立」的前提下进行。** 若实测很差（例如样板工程在最低配上跑不到 25 fps），会在 v1.0 收尾时才暴露，而那时表现力设计已定型——**返工面积是整个 v1.0 而不是一张卡**。
  - 上表三个默认值先拍后改，改的时候要动的是已经有测试、有 fixture、有截图基线的代码。
  - **立下一个判例**：一条卡在外部供给上的门槛可以被重新挂载。下一条卡住的门槛会援引它，而援引它的人不需要再写这么长的一份 ADR——判例的成本从来不体现在第一次用它的时候。
  - 到期版本号写了 `v1.0`，但**今天仓库里没有任何脚本在读过期版本号**（`grep -rl CONSTITUTION-EXCEPTION scripts/` 无输出），而 `NORTH_STAR.md:292` 写着「到期未清理，CI 转为失败」。在门槛可信度修复完成之前，这个到期承诺是一张空头支票。**该修复有了明确落点：`scripts/check-expiry.mjs` 由 T-298 交付（v1.0 · M14 · 波次 W3），它读的就是本条的 `到期 v1.0`。本条的到期承诺自 T-298 完成之日起生效，在此之前它仍然是空头支票——这不是措辞，是排期上的先后关系。**

### 选项 3 · 用软渲数字填附件A 让门槛「通过」（**已排除，登记以免后人重开**）

代价：违反 `附件A:181` 明写的纪律，制造一个将来会被引用的错数字。`docs/BENCHMARK.md` 自己已经写明开发机那一轮「不可作为验收依据」。

### 选项 4 · 默默开工（**已排除，登记以免后人重开**）

代价：宪法第一次被无声破例。`NORTH_STAR.md:292`：「例外必须有到期日。没有到期日的例外，一年后就是新的默认行为。」

## 决定

**选选项 2。产品负责人 2026-08-03 拍板（P-2）。**

下面五条是这次裁决的正式措辞，逐条照办，不许转述：

1. **G0.5-8 不再是「v0.5 晋级 v1 的入口门槛」，改挂为「v1.0 的出口门槛」。** 它在 v1 规划 §7.2 人工验收表里的编号是 **H1**（`MVP_V1_进化规划.md:2324`，归属栏 `v1.0 ⚑`），交付它的三张卡是 **T-279**（bench 页与报告 JSON）· **T-280**（`scripts/apply-bench-report.mjs` 回填脚本与 `--check`）· **T-291**（三档机器实测手册与三机采集）。
2. **`NORTH_STAR.md:140` 的 G0.5-8 那一行保留原文，就地注明「经 ADR-0022 改挂为 v1.0 出口门槛」——不许删行。** 删了就再也看不出它曾经卡在哪一级，而「它被顺延过几次」正是这条门槛现在唯一还剩的约束力来源。
3. **v1.0 即刻合法开工。** 此前已写进 v1 规划与 TASK_BACKLOG_V1 的内容，由本条**追认为合法**；追认这件事的留痕就是本 ADR 的「代价」第 2 条。
4. **门槛本身一个字不放松。** 三台机器（M1 主力 / M2 最低配 / M3 关硬件加速）各一份报告 JSON 入库、`node scripts/apply-bench-report.mjs --check` 绿、M1/M2 非软渲、商务建议线达标或已把实测值写成承诺并签字——四条全过才算 H1 通过（口径逐字见规划 §7.2 H1 行）。**挂载点变了，判据没变。**
5. **这是 `NORTH_STAR §8` 的一次显式破例，到期版本号 `v1.0`。** 四步全走：本 ADR 是第 1 步；第 2 步在代码对应位置留 `// CONSTITUTION-EXCEPTION: §3 · ADR-0022 · 到期 v1.0`；第 3 步由 `scripts/check-expiry.mjs`（**由 T-298 交付**）把这个到期版本号纳入机器读取；第 4 步到期未清 CI 转红。**在 T-298 完成之前，第 3、4 步是空头支票**——这不是措辞问题，是排期上的先后关系（同「选项 2 · 代价」末条）。

代码侧的准备工作（三档机器操作手册 / 报告 JSON schema / 回填脚本 / `--check`）**照常做，且不因选了 2 而缩水**——两个选项都需要它，它不是任何一个选项的沉没成本。

范围界定，避免与相邻 ADR 重叠：

- 本条**只**处理 G0.5-8 的挂载位置。
- G0.5-7 的命令名订正（`pnpm size-limit` → `pnpm size`）与 v1 体积口径（600 → 400 KB）**不在本条**，见 [ADR-0021](0021-撤销-D20-v1.0-引入后处理链.md) 第四条。
- 「到期版本号没有脚本在读」这件事的修复归 **T-298**（`scripts/check-expiry.mjs`，v1.0 · M14），本条只是它的第一个受害者。

## 代价

无论最终选哪一条，下面三条都要付：

1. **时间成本已经付了两次。** G0-7 顺延为 G0.5-8（ADR-0015），G0.5-8 现在又要被处置一次。**第三次顺延不许发生**——本 ADR 无论最终选哪一条，「顺延到下一级」都不在选项里。这一句写死，是为了让下一个想顺延的人必须先推翻它。
2. **拍板本身要占产品负责人的时间**，而在拍板之前，v1 的开工状态在文书上是有瑕疵的。若最终选 2，这段时间已写的代码被追认为合法——**追认这件事必须留痕，就是这一段**。
3. **本条是 `Proposed` 状态，而 v1 规划的其余部分按 Accepted 撰写。** 这意味着规划文档里存在一处「已写好但前提未定」的内容。它不影响任何一张卡的技术内容，但影响「v1.0 现在算不算合法开工」这个陈述——对外沟通时不许含糊过去。
   （**2026-08-03 拍板后，本条已消解**：状态转 Accepted，「前提未定」不复存在。原文保留，因为它记录了 v1 规划从起草到追认之间那段时间的真实状态。）

**拍板选 2 之后，另付第 4 条**：

4. **三份领域设计的关键默认值，在整个 v1.0 期间都是猜的。** 逐条就是「背景」那张表里的三个：**像素比封顶**（`devicePixelRatio` 上限，`design/postfx.md` 的像素比封顶卡）· **剖切平面数量上限**（`design/explode-clip.md`，今天定死为 3）· **描边预设上限**（`composed` 档位，ADR-0021 腿 3 与 `postfx.md:129` 的显存表，今天定死为 2）。选项 1 会让它们在写第一行代码之前就有真数字，选 2 意味着它们在 H1 闭合之前一直是拍的，且会被写进 `frozen-contract.test.ts`（规划 §7.2 H3：**一旦进去就要 ADR 才能改**）。
   **实测不合格时的返工面积是整条表现力线，不是一张卡**：描边、雾、爆炸、剖切、出图五条能力共用同一个 composer 与同一套显存预算，任何一个默认值被实测推翻，五条都要重验；而那时它们已经各自有测试、有 fixture、有截图基线。这条代价与「选项 2 · 代价」第 1 条是同一件事的两个粒度——那条说的是「什么时候暴露」，这条说的是「暴露时要改多大一片」。

## 撤销条件

- **目标机器在 v1.0 任何一个里程碑之前到位** → **立即**执行实测并把门槛挂回原位，无论此前选了哪个选项。不许因为「反正已经挂到出口了」而拖到收尾。
- **v1.0 中期任何一次实测显示样板工程在最低配上不达标** → **立即停止表现力线的新增功能，转入性能专项。** 这条要写死，否则「以后再说」会一直有效——ADR-0015 的撤销条件里已经写过一次同样的话，那一次没有触发，是因为实测从未发生。
- 产品负责人在两个选项之外提出第三条路（例如以客户现场机器的一次远程实测替代）→ 本 ADR 作废重写，不许把第三条路塞进现有两个选项之一的解释里。
- **（已选 2，本条自拍板之日起现行有效）** v1.0 收尾时机器仍未到位 → 门槛到期未清，按 §8 应当 CI 转红；**该转红由 T-298 的 `scripts/check-expiry.mjs` 执行**。若届时 T-298 未完成（因而仍没有读过期版本号的脚本），说明门槛可信度修复没做完，**此时应停止 v1.2 开工**，而不是再顺延一次。
