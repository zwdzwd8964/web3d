# ADR-0012 · 不再默认覆盖 Draco / KTX2 解码器路径

- 状态: Accepted
- 日期: 2026-07-30
- 相关宪法条款: C6；相关反模式: A7

## 背景

C6 要求构建产物零外部运行时请求。Draco 与 KTX2 的解码器是运行时 fetch 的 WASM，
three 的示例从 CDN 取——内网部署即白屏，且总在上线当天才发现（A7）。

据此 T-006 把解码器拷进了 `vendor/`，`AssetLoader` 默认
`setDecoderPath('/vendor/draco/gltf/')`。

编辑器首次构建后发现 three 0.185 的做法已经变了：

```js
// three/examples/jsm/loaders/DRACOLoader.js
const WASM_JS_URL = new URL('../libs/draco/draco_wasm_wrapper.js', import.meta.url).toString()
```

打包器会静态解析 `import.meta.url`，把解码器作为**同源资产**产出到 `dist/assets/`。
换句话说，C6 在这条路径上已经由 three 自身保证了。

而我们的覆盖此时是**净负面**：它把打包器已经解析正确的同源路径，替换成
`/vendor/draco/gltf/`——一个当前没有任何配置去提供服务的路径。Draco 压缩的模型
会加载失败，且失败点离原因很远。

## 选项

1. 保留覆盖，并给编辑器与播放器配置 `vendor/` 的静态服务 —— 与原设计一致；
   多两处构建配置，多一个"忘了配就白屏"的失败面，而收益为零。
2. 去掉默认覆盖，路径改为可选项；`vendor/` 与 `sync-vendor` 保留给确实需要显式路径的部署。
3. 删掉 `vendor/` 与 `sync-vendor` —— 最少的东西；但放弃了非打包部署与
   "解码器放共享位置"这两种场景，而技术方案 §3.2-6 的部署三件套明确要覆盖前者。

## 决定

选 2。`AssetLoaderOptions.dracoPath` / `ktx2Path` 仅在显式传入时才调用 `setDecoderPath`，
常量更名为 `VENDOR_DRACO_PATH` / `VENDOR_KTX2_PATH` 以表明它们是可选项而非默认值。

`scripts/sync-vendor.mjs --check` 继续留在 `check:constitution` 里：它保证仓库中那份
自托管副本与锁定的 three 一致，供上述非打包部署使用。

## 代价

- `vendor/` 目录在默认路径下不再被使用，容易被后来者误认为死代码而删掉。
  已在 loader 的文件头与本 ADR 中说明用途；
- 解码器被打进 `dist/assets/`（Draco 约 700 KB）。对编辑器无所谓，
  但**播放器有 gzip ≤ 400 KB 的预算**（T-105），届时很可能需要把解码器改为按需
  动态加载，或对不含压缩资产的场景整体排除。这条已记入下方撤销条件；
- 与 T-006 卡片的字面描述不一致。

## 撤销条件

出现以下任一情况，改回显式路径（并同时配置静态服务）：

1. T-105 的体积预算因解码器被打进主包而超标，且按需加载无法解决；
2. 升级到某个 three 版本后 `import.meta.url` 的解析不再成立（升级 three 时必须复验：
   构建后确认 `dist/assets/` 里仍有 draco/basis 产物，且产物中无 CDN 域名）；
3. 出现需要多个应用共享同一份解码器的部署要求。
