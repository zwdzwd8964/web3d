# ADR-0009 · 编辑器 3D 层不使用 React Three Fiber

- 状态: Accepted（人工确认，2026-07-30）
- 日期: 2026-07-30
- 相关宪法条款: C2, C3；相关设计决策: D1

## 背景

MVP_V0 §4 的选型表把"编辑器 3D 层"锁定为 React Three Fiber，理由是声明式渲染场景 JSON 开发快。
但 §3 同时把场景图构建、增量 patch 应用、射线拾取、相机与动画全部划给了 `@w3/core`，
并要求 `@w3/player` 不带 React。

两者放在一起会得到一个后果：编辑器用 R3F 从文档声明式地建一棵 three 场景图，播放器用 core
命令式地建另一棵。**这就是反模式 A2「播放器分叉」的镜像版本——分叉的是编辑器。**
届时 parity 测试（T-103）比对的将是两套不同的场景构建逻辑，而它本该证明两侧共用同一套。

D1 还要求"文档一变就派发 patch 到对应 Object3D"，而 R3F 的模型是"状态变则重新渲染 JSX 树"。
两种更新模型叠在一起，`fullRebuildCount === 0` 这条断言会变得无法保证。

## 选项

1. 用 R3F 建场景图，core 只保留加载/射线/动画 —— 贴合 §4 字面；
   代价是 C3 的验证手段（parity）失去意义，且 D1 的增量语义与 R3F 的重渲染语义冲突。
2. 用 R3F 做视口壳，节点仍由 core 建 —— 冲突消失；但此时 R3F 只是包了一个 canvas，
   净收益为负（多一层依赖、多一层生命周期）。
3. 不用 R3F。编辑器视口是一个裸 `<canvas>`，React 只负责把它挂载/卸载并转发尺寸与指针事件，
   canvas 之上的一切由 `SceneRuntime` 命令式拥有。

## 决定

选 3。宪法 C3 位阶高于 MVP 规划的选型表（NORTH_STAR §0："与本文冲突的一切计划…以本文为准"），
且这是唯一能让 parity 测试真正证明 C3 的结构。

`@react-three/fiber` 不安装。编辑器仍是 React SPA，React 管面板、树、表单；3D 归 core。

## 代价

- 视口内的交互（gizmo 拖拽、hover 高亮）要手写命令式代码，拿不到 R3F 的声明式便利，
  这部分开发量确实上升；
- React 与 three 之间的生命周期（挂载、resize、dispose）需要自己接，接错会泄漏 GPU 资源。
  缓解：T-031 的验收项就是"挂载/卸载 100 次后 `renderer.info` 的 geometries/textures 归零"；
- 与 §4 的选型表字面不符，后续维护者对照会困惑（本 ADR 即为答案）。

## 撤销条件

若 v1 的编辑器功能层（特效面板、页面覆盖层编辑）出现大量"3D 对象与 React 组件一一对应"的需求，
且手写桥接代码超过视口代码的一半，则重新评估——但届时正确的做法很可能是把这些需求也收进
core 的注册表，而不是引入 R3F。
