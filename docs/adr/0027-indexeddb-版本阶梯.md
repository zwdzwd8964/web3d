# ADR-0027 · IndexedDB 版本阶梯：`DB_VERSION` 的唯一所有者

- 状态: **Accepted**
- 日期: 2026-08-03
- 相关宪法条款: C4（Schema 向前兼容 —— 本条指出它**只覆盖了两条兼容链中的一条**）· C7（存储走抽象层）
- 承接卡: **T-202**

## 背景

`IndexedDbProvider` 的 `DB_VERSION` 从 v0 至今是 **1**，仓库里**零 IndexedDB 迁移先例**。

v1 的三份领域设计各自需要一个新 object store，且**各自把 `DB_VERSION` 写成 2**：

| 设计 | 要的 store | 落地卡 |
|---|---|---|
| debt-ops（崩溃恢复 / 跨标签页租约） | `drafts` · `leases` | T-286 · T-287 |
| multi-scene（多场景） | `scenes` | T-427 |
| backend（文档修订，冲突三选一） | `revs` | T-406 |

IndexedDB 的 `upgradeneeded` 回调**只在版本号真的上升时触发**。于是：第一个落地的把所有用户的库升到 2；第二个也写 2，那些用户的 upgrade **永远不会执行**，他们的库里永久缺两个 store。没有报错，没有告警。

**这不是排期问题，是 blocker，理由在下面这一句**：

> 三份设计**各自写了一条「v1 库 → v2 provider」的回归测试，三条都会绿**——因为每条都只在自己新建的 fixture 上跑。会坏的那个情形是「库已经在 2 了」，而仓库里没有任何东西看它。

还有一层更基础的：**这是与 `schemaVersion` 完全独立的第二条向前兼容链**。铁律 4 的三件套（`schemaVersion` +1 · 一个 `Migration` · 一份 fixture）一个字都不覆盖它，`CLAUDE.md` 的 DoD 清单里也没有对应条目。用户本地库是**尚未发布的工作的唯一副本**——它比任何一份历史快照都更不能坏。

## 选项

### 选项 1 · 各卡各自升版本，靠评审拦

- **收益**：不需要提前决定任何东西；每张卡自洽。
- **代价**：这正是被否掉的现状。三份设计已经证明「靠评审拦」在合并阶段就失败了一次——**三份稿子同时写了 2，没有任何机器发现**。而它的失败是静默的、只对**已经升级过的**用户发生的、且被三条各自为政的绿色回归测试掩盖的。修复成本是一次全量数据迁移脚本，而那时用户的库已经在生产里。

### 选项 2 · 一次建齐四类 store，指定唯一所有者（**采纳**）

- **做什么**：`DB_VERSION = 2` 一次到位，`drafts` / `leases` / `scenes` / `revs` 四个 store 在同一次 upgrade 里创建，**只建结构不写数据**。v1 全程只有 T-202 能动这个常量。
- **收益**：三条链的冲突在写第一行功能代码之前就消失了；后续三张卡各自只往既有 store 里写内容，零版本变更；「库已经在 2 了」这个情形由 T-202 的 `idb-upgrade.test.ts` 直接覆盖。
- **代价**（见下）。

### 选项 3 · 每张卡一个版本号（2 / 3 / 4 / 5）

- **收益**：每个 store 的引入时机与它的卡一一对应，历史最清晰。
- **代价**：四次 upgrade 意味着四条必须**按顺序**成立的迁移路径，且用户可能从 1、2、3、4 任一版本跳上来 —— 组合数从 1 条变成 10 条，而其中大部分永远不会有人真的跑到。为一个「历史清晰」买十条测试路径，与本项目「预算是用来约束的」的取舍方向相反。

## 决定

**采纳选项 2。**

1. `DB_VERSION = 2`，四类 store（`drafts` / `leases` / `scenes` / `revs`）在 T-202 一次建齐，全部只建结构不写数据。
2. **唯一所有者是 `packages/storage/src/idb-provider.ts`，唯一改它的卡是 T-202。** T-286 / T-287 / T-406 / T-427 只在既有 store 里加内容，**不动版本号**。
3. upgrade 函数只允许 `if (!db.objectStoreNames.contains(x)) { … }` 形式的新增，**只增不改不删**。理由与 C4 同构：判据写成「目的地长什么样」而不是「历史走过哪条路」，函数才是幂等的，用户以任何路径到达版本 2 都会得到同一个库。
4. **v1.5 的 T-428 若确需升到 3，必须先回到本 ADR 追加一行**，写明谁升、为什么不能塞进既有 upgrade、以及从 1 和从 2 两条路径各自的回归用例。追加行之前动 `DB_VERSION` 的 PR 一律打回。

## 代价

1. **四个 store 里有两个要到 v1.5 才有第一个消费者**（`scenes` / `revs`）。在那之前它们是每个用户库里两个空壳。代价是真实的：一个空 store 是一条没有测试保护的结构承诺，如果 v1.5 最终决定换形状（例如 `revs` 改成按 project 分库），今天建的这个就是纯浪费，且**删不掉**——按第 3 条，upgrade 只增不删。
2. **本条把「谁能改 `DB_VERSION`」变成了一条人读的规矩，而不是一道机器闸门。** T-202 没有交付「改 `DB_VERSION` 就 CI 红」的脚本。这是有意识的取舍：写那道闸门要么靠 git diff 检查（脆），要么靠一份需要同步维护的期望值清单（第二份真相）。**因此这一条依赖评审，而本 ADR 的背景一节刚刚论证过「靠评审拦」失败过一次。** 缓解手段只有一个：`idb-upgrade.test.ts` 里那条「store 集合双向相等」的断言——改了版本却漏建 store 时它会红，但改了版本而建全了 store 时它不会。
3. **`scenes` / `revs` 的 `byProject` 索引形状是现在拍的**（`keyPath: 'projectId'`）。v1.5 真写数据时若发现记录里 projectId 不在顶层，索引要重建，而重建索引需要升版本——即触发第 4 条。

## 撤销条件

出现下面任何一条，回来重开这个决定：

- **v1.5 发现 `scenes` 或 `revs` 的记录形状与 `byProject` 索引不兼容**，索引必须重建。此时第 4 条被触发，本 ADR 追加一行而不是新写一条。
- **v1.5 决定后端模式下不再使用本地 IndexedDB 存修订**（`revs` 由服务端承担）。此时 `revs` 成为一个永远为空的 store，应当在下一次版本变更时评估是否值得保留——注意按第 3 条它不能被删除，只能被忽略，所以这条撤销条件的实际产物是一行文档而不是一次清理。
- **出现第五个需要新 store 的领域。** 一次建齐的收益建立在「我们知道 v1 全部需要什么」这个前提上；这个前提一旦被证伪，说明应当改为选项 3 的分次升级并接受它的组合测试成本。
