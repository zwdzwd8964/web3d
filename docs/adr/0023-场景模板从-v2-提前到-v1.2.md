# ADR-0023 · 场景模板从 v2 提前到 v1.2，并重述 v2 晋级门槛

- 状态: Accepted
- 日期: 2026-08-03
- 相关宪法条款: NORTH_STAR §3（v2 新增清单 `:158`、v2 晋级门槛 `:160-163`）· §5（改本文须留 ADR）· §1 NSM

## 背景

`NORTH_STAR.md:158` 把「项目模板 / 场景模板」明确列在 **v2** 的新增清单里。[ADR-0020](0020-v1-拆成三级台阶.md) 的版本切分把「规则模板与场景模板」放进 **v1.2「编排与复用」**。`NORTH_STAR §5` 规定「修改本文的任何一条」必须留 ADR——**在本条批准之前，模板相关任务卡不能开工，开了就是 agent 自行改宪法。**

推动它提前的不是模板本身，而是模板背后暴露的一个**与模板无关的独立缺口**：

> **「新建项目」这条能力链今天完全不存在。**
> `createEmptyDocument`（`packages/schema/src/factory.ts:46`）在生产侧零调用者，全部调用点是 `packages/schema/test/{factory,scale}.test.ts` 与 `scripts/bench-scale.mjs:14`（`design/reuse-demo.md:24`）。

这正是 T-137 同形的又一次复发：每一环都建好了，没人负责入口。v1.0 的机械守卫（成员级零调用者检查）一上线就会把它抓出来——`createEmptyDocument` 是一个**完整实现 + 有单测 + 零生产调用者**的教科书样本。

## 选项

1. **留在 v2。**
   - 收益：宪法一字不改。
   - 代价：v1.0 / v1.2 的「能演示、能卖」少一个卖点；`createEmptyDocument` 继续零调用者；「新建项目」继续不存在——而这个缺口会在 v1.0 的样板工程演示里立刻暴露：客户看完泵组样板，问「那我自己新建一个」，答案是没有这个按钮。

2. **提前到 v1.0。**
   - 收益：与样板工程同一版本交付，冷启动入口一次做完，不返工。
   - 代价：v1.0 已是 147 张 / ≈148 人日（ADR-0020 背景），再压进「新建项目 + 模板网格」这条约 2.5 人日的新链；而它与 v1.0 的三个词（能演示、能卖、能被嵌进别人的系统）没有一个是强相关的——模板解决的是「第二个场景怎么起步」，v1.0 解决的是「第一个场景能不能交付」。

3. **提前到 v1.2（本条）。**
   - 收益 / 代价见「决定」与「代价」。

4. **只做规则模板，场景模板留 v2。**
   - 收益：工作量最小。
   - 代价：规则模板没有场景模板配套时，用户仍只能从样例场景改起；且它**完全没有解决**「新建项目」这个独立缺口——选项 4 恰恰是暴露该缺口与模板无关的那个证明。

## 决定

选 3。**场景模板与规则模板一并放在 v1.2「编排与复用」。**

理由：它与 v1.2 的另一半（flows / pages 编排）是同一件事的两面——编排产生的那一堆「事件 → 条件 → 动作」配置，正是模板要打包复用的东西。把模板与编排放在同一级，模板的第一批出厂内容就有真实来源，而不是凭空设计几个示范模板。而 v1.0 的三个词里没有一个需要模板。

同时定死三条边界，避免 v1.0 与 v1.2 各做各的：

### 1 · 样板工程不是场景模板 —— 样板工程留 v1.0，模板机制留 v1.2

`design/reuse-demo.md:48` 已经把这条说清楚：**场景模板是「从哪儿起步」，样板工程是「做完长这样」。** 把两者合成一个概念会立刻产生一个坏结果：样板工程为了当模板，必须让用户先绑 4 个槽位，而它的全部价值恰恰是**打开就能演示**。

### 2 · v1.0 必须自带一个不依赖模板机制的项目入口

具体是两项固定入口：「新建空项目」与「打开泵组样板工程」。**这一环必须在 v1.0 的台账里有卡认领**，不许挂在 v1.2 头上——否则 v1.0 交付时 `createEmptyDocument` 仍然零调用者，而机械守卫会在 v1.0 的 CI 上转红。

这是 v0.5 那条教训（**能力链每一环都要有卡认领**）在跨版本切分上的直接应用：一条能力链被两个版本切开时，切口两侧各归谁，必须在切开的当天写下来。

### 3 · 出厂模板的反向守卫与模板同卡交付

v1.2 的出厂模板会引用 v1.0 注册的动作（爆炸 / 剖切 / 描边）。`requires` 过滤保证模板不会引用一个不存在的动作，但**反向守卫**——「出厂模板在默认注册表下一个都不会被过滤掉」这条断言（`reuse-demo.md:295-298`）——必须与模板同卡交付。没有它，一个 `requires` 写错的模板会变成**永远不显示的死代码**，且周边测试全绿。这又是 T-137 同形。

**变异检验**：把任一出厂模板的 `requires` 改成一个不存在的动作名，反向守卫必须转红。

## 代价

明确接受五条：

1. **v2 的晋级门槛必须重新表述。** `NORTH_STAR.md:162` 的「新客户的定制需求 100% 落在『新增注册项』或『配置』两类」**正是靠模板兑现的**——模板是「配置」这个词在产品上的具体形态。模板已在 v1.2 存在并被本客户用过，v2 就失去了一块纯粹的观测面：它不再能回答「模板机制是否成立」，只能回答「模板内容是否够用」。
   新表述要改成一个仍然可观测的问题，例如「模板是否已足以覆盖第二个客户的起步场景，且未新增模板机制代码」。
   > ⚠ **待产品负责人确认**：`NORTH_STAR.md:160-163` 三条 v2 晋级门槛的新表述**只能由人写**。本 ADR 指出它必须改、并说明为什么必须改，但不代写——替 v2 拍门槛正是 §5 要防的事。

2. **改宪法本身有成本。** v2 清单少一项、v2 门槛改写，所有后续 agent 的口径要同步；IMPL_NOTES 与勘察记录里引用旧表述的地方会有一段时间不一致。

3. **v1.0 与 v1.2 各有一个项目入口实现**（v1.0 的两项固定入口 + v1.2 的模板网格），第二次做时要改第一次的 UI，返工面约半张卡。**这是明确接受的重复，不是疏漏**——把它写在这里，是为了让 v1.2 那张卡的预估里包含这半张。

4. **模板与 v1.0 表现力字段之间产生一条跨版本依赖。** v1.0 冻结 schema 时必须把模板要用到的形状一并冻住（ADR-0020 决定第 1 条）；v1.2 开工时若发现漏了字段，按同一条纪律**登记 v2，不追加**——也就是那个模板做不成，不是 schema 再 bump 一次。

5. **NSM 的第一次真实读数被推迟。** §1 的北极星指标是「不改 core 能配出多少种交付级场景」，模板是它最直接的度量工具。放到 v1.2 意味着 v1.0 收尾时这一格仍然只能填「—」。

## 撤销条件

- v1.2 开工时「新建项目 + 模板」这条链的实际耗时超出预估 2 倍（`CLAUDE.md` 停工条款第 6 条）→ 场景模板退回 v2，只保留规则模板与项目列表。
- 场景模板在真实使用中被证明用户永远选「空场景」→ 退回 v2，本 ADR 标 Superseded；此时 `NORTH_STAR.md:158` 的 v2 清单恢复原样，而 v2 门槛的改写**不恢复**（因为「新建项目」这条链已经在 v1.0 交付了，它本来就不该被算进 v2 的检验面）。
- **v2 门槛的新表述迟迟没人写** → 说明这条提前没有被真正接受。此时应把模板整体退回 v2，而不是让 v2 带着一条自相矛盾的门槛进场——一条已知失效的门槛比没有门槛更危险（同 [ADR-0026](0026-改写恒真的后端晋级门槛.md) 的判断）。
- 若 v1.0 的两项固定入口最终没有卡认领 → 说明本 ADR 的第 2 条边界没有落地，应在 v1.0 收尾审查里作为 blocker 登记，而不是顺手补进 v1.2。
