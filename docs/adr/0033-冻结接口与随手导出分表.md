# ADR-0033 · 零调用者豁免表拆成两张：冻结接口与随手导出

- **日期**：2026-08-05
- **任务卡**：无（跨卡裁决，由 T-237 的批次报告上交，产品负责人 2026-08-05 选定选项 B）
- **相关**：D36（守卫的扫描面下限）· 门槛 G1.2-9（豁免表条数只降不升）· NORTH_STAR §8（例外必须有到期版本号）· [ADR-0020](0020-v1-拆成三级台阶.md)（schema 在 v1 只 bump 一次）

## 背景

`MAX_EXEMPTIONS` 这个棘轮的规矩是「只降不升」，它是门槛 G1.2-9 的全部实现。
**连着三张卡把它推了上去**：

| 卡 | 从 | 到 | 推上去的那个符号 |
|---|---|---|---|
| T-225 | 34 | 35 | `schema:EXPLODE_MODE_LABELS` |
| T-235 | 35 | **33** | （唯一一次下降：接线四条接缝） |
| T-240 | 33 | 35 | `RuntimeContext.highlightOf` · `SceneRuntime.highlightOf` |
| T-237 | 35 | 36 | `ClipPlayer.mixerCount` |

三次上调的理由是**同一条**，而且每次都写在了棘轮记录里：v1.0 正按规划 §4 的冻结清单
交付 API（`highlightOf` / `captureImage` / `setExplode` 是那份清单里 `RuntimeContext`
的 +3），而消费这些 API 的卡排在 v1.2 与 v1.5。CLAUDE.md 停下来问人第 8 条把 §4 冻死了：
**开工后发现漏字段要登记 v2，不许追加**，所以「等消费者来了再落 API」不是一个合法选项。

于是每张按清单交付的卡都会把棘轮往上推一格。**一个每张卡都要上调的上限，不是上限，
是记账簿。** 而记账簿挡不住它真正要挡的那件事：随手 `export` 一个没人用的东西。

## 决策

**把这个文件拆成两张表**，按一个问题分：**这个导出写在冻结规范里了吗？**

| | 豁免（四列） | 冻结接口（五列） |
|---|---|---|
| 收什么 | 归得到某张卡、但今天确实没人调 | 规划 §4 / SCHEMA_SPEC / ECA_SPEC 里**逐字冻结**、消费者排在后面版本 |
| 条数棘轮 | **有**，`MAX_EXEMPTIONS` 只降不升 | **无** |
| 进表门槛 | 人工审查（reason ≥ 10 汉字、owner 是真卡号） | **机械门锁**：符号名必须逐字出现在 `spec` 列点名那节规范的**代码跨度**里 |
| 到期 | NORTH_STAR §8，到期未清转红 | **一字不改**，同样到期转红 |

第三张表（v0/v0.5 遗留基线）不动。

`MAX_EXEMPTIONS` 随本次迁移 **36 → 26**：十行迁出去，四列表回到只装「归得到卡但今天
没人调」的东西。这不是靠接线换来的下降，是靠分类——**记在棘轮记录里时要说清楚这一点**，
否则下一个人会以为有人一次清了十条债。

### 为什么可以不设条数上限

因为这张表的长度**不由写表的人决定**，由冻结清单决定，而冻结清单自己就是冻的。
再加一行，要么那个符号已经在 §4 里（那么它本来就该交付），要么写不进去（那么门锁拦下它）。
给它另设一个上限，只会把 T-225 那种「每交付一次就要上调一次」的循环原样复制一遍。

### 门锁的实现，以及第一版被击穿的地方

`assertNamedInSpec` 去 `spec` 列点名的那一节里找符号名。第一版只查「这个词出现在这一节里」，
**当场被 `schema:touch` 击穿**——规划 §4 的一段 JSDoc 里写着
`"fill in missing fields with defaults and touch nothing that is already there"`。
一个散文里的英文单词就够了。

所以最终版只认两种位置：**行内代码跨度**，以及**围栏代码块里注释以外的部分**。
`touch` 因此留在四列表里，由条数棘轮管着。

另外两条，都是 D36 的 M6 形状：

- **小节标题找不到 = 失败**，不是「退回全文件」。退回去等于门锁悄悄松开一整级。
- **抽出的标识符数有下限**（`MIN_SPEC_IDENTIFIERS = 200`，实测 1000+）。实测证明这条不是
  装饰：把下限连同「读不到就失败」一起拿掉、再写成「抽不到标识符就放行」，守卫**一行不报、
  直接 PASS**，而它其实什么都没读。

## 代价

1. **一个文件里两张表，读的人要先分清自己该往哪张写。** 文件头加了一张三行的索引表，
   守卫的报错也点名是哪张表，但这仍然是一次认知成本的净增加。
2. **门锁与规范耦合**。规划 §4 的标题一改、或者哪天 §4 被拆成 §4.1/§4.2 另起 `##`，
   守卫会红——报的是「读不到规范」而不是逐行报，方向是对的，但它确实是一处新的脆弱点。
3. **「写进规范」成了绕过条数棘轮的路径**。理论上有人可以先往 §4 里加一行、再往冻结表里加一行。
   但 §4 由停下来问人第 8 条守着（改它必须上交），所以这条路径要穿过一次人工裁决——
   **这正是设计意图**，不是漏洞：代价从「守卫拦不住」变成「必须有人签字」。
4. **不设上限意味着这张表可以长得很长**。到期日是唯一的自动收缩力量，而最远的一行是 `v2`。

## 撤销条件

出现下面任何一条，就把两张表合回去并给合并后的表重设一个上限：

- 冻结接口表长到 **30 行以上**，且其中超过三分之一的 `owner` 指向同一张卡——那说明它已经
  不是「按清单交付」，而是某张卡在囤积接口。
- 门锁被绕过一次：有人为了让某个符号进这张表而去改了规划 §4（`git log docs/MVP_V1_进化规划.md`
  出现「为守卫加词」类的提交）。
- v1.2 收口时，这张表里到期的行**超过一半没有被消费**——那说明「消费者在后面」这个前提本身
  是假的，问题不在分表而在排期。
