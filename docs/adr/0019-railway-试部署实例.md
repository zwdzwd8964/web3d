# ADR-0019 · Railway 试部署实例：单服务同源静态托管 editor + player

- 状态: Accepted
- 日期: 2026-08-02
- 相关宪法条款: C6（断网能跑——本 ADR 划清「构建时联网」与「运行时零外部请求」的边界）、C7（存储只见接口——部署形态不引入任何服务端存储）
- 相关任务卡: 无（临时请求：开一个可公网访问的实例做实地测试；离网交付构建属 T-173，不在本 ADR 范围）

## 背景

需要一个能从公网访问的实例做实地测试：在真实网络与真实设备上走一遍黄金路径
（编辑 → 发布 `.w3p` → 播放器打开）。仓库此前**没有任何部署配置**——这是刻意的：
产品定位是客户内网离线交付，交付物是 `dist/` 静态文件，放到哪个 Web 服务器上
不归引擎管。

但「试部署到 Railway」需要回答三个此前没人回答过的问题：
用什么构建（Railway 侧没有现成 pnpm monorepo 约定）、用什么进程托管静态文件
（仓库没有服务端代码）、editor 和 player 是一个服务还是两个。规范对此全无着墨，
按铁律 12 先记录选择。

## 选项

1. **单服务 · Docker 多阶段构建 · 自写零依赖 Node 静态服务器**：
   编辑器挂 `/`，播放器以 `--base=/player/` 构建挂 `/player/`，同一个origin。
   - 收益：一个实例一份账单；同源意味着「发布下载 `.w3p` → 拖进 `/player/`」全程
     不碰跨域；Dockerfile 把 Node/pnpm 版本钉死（与 CI 同为 Node 24 + pnpm 11.12.0），
     不依赖 Railway 构建器对 monorepo 的探测；运行时镜像只有 `node:24-slim` +
     两个 dist + 一个 ~180 行的服务器文件，不引入任何新第三方依赖（停下来问人
     规则第 3 条因此不触发）。
   - 代价：静态服务器要自己养，见下节。
2. **两个 Railway 服务分别托管 editor / player**：
   - 收益：各自可独立伸缩、独立域名，`--base` 保持默认 `/`。
   - 代价：双份实例费用；两个域名让「编辑完打开播放器验证」多一步心智负担；
     试部署阶段没有任何需要独立伸缩的理由。
3. **Railpack/Nixpacks 自动构建 + `vite preview` 托管**：
   - 收益：零新增文件。
   - 代价：`vite preview` 官方定位是本地预览，不做生产承诺；运行时镜像必须携带
     全部 devDependencies；自动探测对「workspace 里两个应用」这种形状经常猜错，
     猜错的报错发生在 Railway 侧而不是本地，调试回路长。
4. **换静态托管平台（Pages 类产品）**：
   - 收益：免进程管理。
   - 代价：用户点名 Railway；且 Pages 类平台的构建环境同样要解决 monorepo 探测，
     没有省掉本 ADR 要回答的任何问题。

## 决定

选 1。新增四个文件，全部与包代码零接触：

| 文件 | 职责 |
|---|---|
| `Dockerfile` | 阶段一 `node:24-slim` 装 pnpm 11.12.0、`--frozen-lockfile` 安装、构建两个 SPA（player 加 `--base=/player/`）；阶段二只拷两个 `dist/` 和服务器文件 |
| `deploy/server.mjs` | 零依赖静态服务器：读 `PORT`（Railway 注入）、绑 `0.0.0.0`、`/healthz` 健康检查、路径穿越防护、`.wasm`/`.glb`/`.ktx2` 等正确 MIME、哈希资产 `immutable` 其余 `no-cache`、gzip、SIGTERM 优雅退出 |
| `railway.json` | 钉死 DOCKERFILE 构建器 + `/healthz` 健康检查，Railway 侧无需任何手工配置 |
| `deploy/README.md` | 面向操作者的开实例步骤与本地验证命令 |

播放器的 `--base=/player/` 只出现在 Dockerfile 的构建命令里，`vite.config.ts` 不动
——本地 `pnpm dev` / `pnpm build` / CI / 体积预算全部维持原状，感知不到部署的存在。

## 代价

明确接受四条：

1. **自写服务器不是 nginx。** ~180 行覆盖了 MIME、穿越防护、缓存、gzip、健康检查，
   但没有 Range 请求、没有 ETag、没有限流。对试部署够用；**若这个实例被拿去当生产**，
   应换成 nginx/Caddy 或客户内网既有的 Web 服务器——那是交付形态，不是本 ADR 的形态。
2. **公网实例与产品的内网离线定位无关。** 它只用于实地测试与演示。访问者的场景数据
   仍在其浏览器 IndexedDB 里（C7 未被触碰），服务器上不落任何用户数据，因此也
   **不能**指望两台设备通过这个实例互通数据——同步不存在，这是产品定位不是缺陷。
3. **部署构建发生在 Docker 里，不复用 CI 产物。** player 因 `--base` 不同与 CI 的
   dist 不是同一份字节。试部署阶段接受双份构建；若未来要「CI 产物即部署产物」，
   届时把 base 决策上移。
4. **镜像构建时需要访问 npm registry。** C6 约束的是**运行时**零外部请求（构建产物
   已由 `check-no-external.mjs` 扫描），构建时联网不违宪；真正的断网构建（预置
   store）归 T-173，本 ADR 不解决。

## 撤销条件

出现下列任一信号时重新考虑：

- 要给真实客户交付（内网/离线）——本方案不适用，回到「拷 `dist/` 进客户 Web 服务器」
  的交付路径，本 ADR 的产物不得混入交付物；
- 实地测试中发现自写服务器缺的能力（Range、ETag）真实挡路——换 Caddy/nginx 镜像，
  届时废除 `deploy/server.mjs`；
- 产品长出真实后端（协同、账号、云存储）——单静态服务架构作废，部署形态整体重议；
- Railway 侧对 Dockerfile 部署的行为发生变化（PORT 注入、健康检查语义）——按平台
  文档重估 `railway.json`。
