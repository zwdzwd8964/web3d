# ADR-0008 · 动作定义以数据导出，由 registerBuiltinActions 集中注册

- 状态: Accepted
- 日期: 2026-07-30
- 相关宪法条款: C5, C8

## 背景

ECA_SPEC §4.3 的示例在模块顶层直接调用 `registerAction({...})`，即"导入即注册"。
这使 `import` 具有副作用：测试文件的导入顺序会影响全局注册表内容，
而 §9.1 要求 ECA 单测快且不 flaky。

## 选项

1. 照抄"导入即注册" —— 与示例逐字一致；测试之间通过全局注册表互相污染，
   且无法让某个测试在干净注册表上验证"缺必填项即抛错"。
2. 各 group 导出定义数组，`registerBuiltinActions(registry)` 集中注册 —— 导入无副作用，
   测试可各自 `new ActionRegistry()`；新增动作的改动文件数不变（仍是 group 文件 + 实现 + 测试）。

## 决定

选 2。保留 `registerAction` / `getAction` / `allActions` 的模块级 API（作用于默认注册表），
同时提供 `ActionRegistry` 类供测试与未来的多实例场景使用。

## 代价

- 与 §4.3 示例的写法不一致，照着规范写新动作的人会先写成 `registerAction(...)`，
  然后发现没生效（定义未被加入 group 数组）；
- 多一个 `BUILTIN_ACTIONS` 数组要维护，忘记加入即该动作不存在。
  缓解：`actions.test.ts` 的 G0-5 门槛会因"注册表里有、测试清单里没有"而失败，
  但反向（写了定义却没加进数组）不会被抓到。

## 撤销条件

若上面那个反向盲区在实践中真的漏过一个动作，改为在 group 文件末尾用一个
`export const XXX_ACTIONS = [...]` 的 lint 规则强制列举，或回到导入即注册并给测试加显式重置。
