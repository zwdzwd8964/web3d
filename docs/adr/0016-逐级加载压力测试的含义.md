# ADR-0016 · 「逐级加载压力测试」实现为场景副本倍增阶梯

- 状态: Accepted
- 日期: 2026-07-31
- 相关宪法条款: C1（不改文档）、C8（可测边界）
- 相关任务卡: T-116（清偿 T-110 缺项）、T-174（灯光/阴影压力档将复用本阶梯）

## 背景

T-110 卡片列出 benchmark 页面必须包含六项：WebGL2 检测、帧率、drawcall、三角形数、
贴图显存估算、**逐级加载压力测试**。前五项已交付，第六项没有。对抗式审查把它记为 minor，
T-116 要求补上。

问题是：**「逐级加载压力测试」这个词在任何规范里都没有定义。** 卡片引用的技术方案
§3.2-5 并不包含这段文字（全文搜索 `逐级`、`压力` 只命中无关段落）。按铁律 12，
不许静默做假设，所以先记录选择。

## 选项

1. **场景副本倍增阶梯**：把已加载的场景整体克隆 ×1 / ×2 / ×4 / ×8 挂进渲染场景，
   每档测一段帧时间，报告「这台机器还能撑住几份这样的场景」。
   - 收益：回答的是验收现场真正会被问的问题——"我们的模型比这个大三倍，跑得动吗"；
     产出一个可写进附件A 的承载上限；与 T-174 的「灯光/阴影档位」形状一致，能复用。
   - 代价：克隆共享几何与材质，所以只压 drawcall / 顶点吞吐，**不压显存**；
     真实的大模型还会有更多材质与贴图，本项给出的是乐观上界。
2. **分级加载耗时拆解**：把一次加载拆成解包 / 解析 / GPU 上传 / 首帧，逐级计时。
   - 收益：定位"打开慢"卡在哪一级。
   - 代价：它测的是加载，不是压力；且四级里有三级取决于磁盘与解压，换台机器结论就变，
     对"能不能跑"这个验收问题没有回答力。
3. **不做，把卡片这一项划掉**。
   - 收益：零成本。
   - 代价：T-110 的交付与卡片字面不符，且这正是 v0 收尾审查抓到的那类"悄悄缩范围"。

## 决定

选 1。「逐级」= 一级一级加压的档位，「加载」= 加载进场景的内容量，
「压力测试」= 一直加到跌破帧率门槛为止。

阶梯为 ×1 / ×2 / ×4 / ×8 份场景副本，每档测约 1.2 秒；某一档跌破 `fpsFail`（25）后
不再往上加。报告一行「承载上限」= 仍然 ≥ `fpsWarn`（45）的最大份数，附该档的
drawcall 与面数。评级函数 `gradeStress` 放在 `metrics.ts`，可在纯 Node 单测。

副本直接 `clone(true)` 后挂到 `runtime.scene`，**不进文档**：它是测量装置，不是场景内容。
清理时只 `remove` 不 `dispose`——克隆共享原件的几何与材质，dispose 会把原件一起销毁。

## 代价

明确接受三条：

1. **本项测不出显存墙。** 副本共享贴图，所以 ×8 的显存与 ×1 相同。真实的"八倍大场景"
   通常也带八倍贴图，那种场景会先撞 `maxTextureBytes` 而本测试看不见。报告里写明这一点，
   附件A 引用时必须一并抄上这句限定。
2. **测得的是当前相机取景下的吞吐。** 副本沿 X 轴平移排开，视锥剔除会剔掉一部分，
   所以 ×8 并不等于 8 倍绘制开销。数值用于**同一台机器上不同模型之间的相对比较**，
   与帧率数据同一性质。
3. **多花约 5 秒测量时间**（四档 × 1.2 秒）。benchmark 页总时长从 ~6 秒增至 ~11 秒。

## 撤销条件

出现下列任一信号时重新考虑：

- 客户现场真正卡住的是显存而不是 drawcall（届时本阶梯该换成"贴图倍增"或直接改测显存）；
- T-174 的灯光/阴影档位落地后发现两套阶梯逻辑无法共用，说明抽象选错了；
- 技术方案或附件A 后续给出了「逐级加载压力测试」的正式定义，且与本文不同——以规范为准，
  本 ADR 作废。
