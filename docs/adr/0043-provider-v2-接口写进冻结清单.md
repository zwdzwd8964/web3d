# ADR-0043 · `StorageProvider` v2 的接口写进规划 §4，而不是抬棘轮

- **状态**：Accepted
- **日期**：2026-08-11
- **任务卡**：T-286
- **相关**：[ADR-0033](0033-冻结接口与随手导出分表.md)（冻结接口与随手导出分表）· X-27（facet 扩张纪律）· 台账新纪律 8（provider 三件套）· NORTH_STAR §8（到期检查一字不改）

---

## 背景

T-286 要给 `StorageProvider` 加一批 v1.5 才有消费者的类型：11 个值类型 + 五个 optional
facet。卡面明写 **facet「全是类型，无实现」**——那是 X-27 的裁决：凡是不是所有 provider
都能实现的，一律 optional facet；接口本体只放每一个 provider 都做得到的东西。

于是它们全部是**零生产调用者的导出**，而 `check-dead-exports` 有三张表：

| 表 | 收什么 | 有条数上限吗 |
|---|---|---|
| 四列豁免表 | 归得到卡、今天没人调 | **有**，`MAX_EXEMPTIONS` **只能降不能升** |
| 冻结接口表 | 规划 §4 / 两份 SPEC 里**逐字冻结**、消费者排在后面版本 | 无，改由「必须写进规范」这把门锁把关 |
| v0/v0.5 遗留基线 | 历史存量 | 有，`MAX_LEGACY` 只降不升 |

落地时 `MAX_EXEMPTIONS` **正好是 20/20**——这一批里它已经三次向下走（24 → 21 → 20），
每一次都是靠真的接上调用者换来的。

## 决策

**把这批接口写进规划 §4（新增 §4.6），走冻结接口表。**

四条路里其余三条都不通：

| 选项 | 为什么不 |
|---|---|
| 进四列豁免表 | `MAX_EXEMPTIONS` 只能降不能升，而它此刻在顶。为一张卡把它抬三倍，等于宣布这道棘轮可以被抬——而它挡住过的东西记在 ADR-0033 的账上（T-243 差点为了让一条测试有东西可断而新增 `sectionPlaneCount`，闸门当场判它是孤儿） |
| 不导出 | facet 的全部意义就是给 v1.5 的 `HttpApiProvider` 用。不导出等于不做 |
| 现在就给实现 | 与 X-27 的裁决直接冲突：`MemoryProvider` 挂一个空的 `locks` 正是那条纪律要防的东西 |

### 这不违反 §4.0 的「一次性冻结」

§4.0 冻的是 **`SceneDocument` 的字段、动作与事件**——那三样一次 bump 全落地，
「开工后发现漏字段 → 登记 v2，不追加」（ADR-0020 决定第 1 条）说的也是它们。

`StorageProvider` 不在 `SceneDocument` 里、不 bump `schemaVersion`，**铁律 4 完全覆盖不到
它**——这正是台账新纪律 8（provider 三件套：接口 + 两实现 + 契约测试）存在的理由。
两条纪律管的是两样东西，§4.6 落在新纪律 8 这一侧。

### 门锁没有被绕过

冻结接口表能不受条数限制的全部理由，是它的门锁：**符号名必须逐字出现在 `spec` 列点名的
那节规范的代码跨度里**。§4.6.2 是一段围栏 TypeScript 代码块，每一个进表的符号都在里面。
一个「随手加的、没人用的」导出写不进 §4.6，也就进不来这张表——门锁的强度一点没变，
变的只是这一节规范存在了。

## 代价

1. **§4 在 v1.0 内被补写过一次。** 它自称是「一次性冻结」的清单，而现在多了一节。
   如实记：**冻结的是 `SceneDocument` 那三样，不是这份文档的字数**——但这个区分只写在
   §4.0 与本 ADR 里，下一个读 §4 标题的人仍然可能读成「§4 可以随时加」。
   缓解办法是 §4.6 开头那段 ⚠ 与本 ADR 的链接，仅此而已。
2. **约 40 行冻结接口，全部到期 v1.5。** 到期未接线会照 NORTH_STAR §8 转红，而 v1.5 的
   后端线本来就要接它们——所以这是一张**会自己收敛的账**，前提是 v1.5 真的做。
   v1.5 若被推迟，这 40 行会在到期那天一次性红出来，那时要么接线要么改到期版本号，
   而改到期版本号是一次需要理由的动作，不是顺手改一个数。
3. **facet 的形状今天没有任何实现验证过。** 它们是照 v1.5 的设想写的，而 v1.5 的第一个
   实现很可能发现某个签名不好用。届时改它们要同时改 §4.6 与冻结接口表两处——
   比只改代码贵，这是「先冻规范」的固有代价。

## 撤销条件

- v1.5 的 `HttpApiProvider` 第一次落地时，若发现 facet 的切分与真实分工不符（例如
  `revisions` 与 `audit` 实际上必须一起实现），应当合并它们并**同时**订正 §4.6——
  那时本 ADR 的「五个 facet」不再成立，但「写进规范再进冻结表」这条路径仍然成立。
- 若将来出现第二次「一批零调用者导出撞上棘轮」而它**写不进任何一份冻结规范**，
  那说明这条路径被当成了绕过棘轮的通道——届时应当回到抬棘轮与拆卡两条路上重新裁决，
  而不是再补一节规范。
