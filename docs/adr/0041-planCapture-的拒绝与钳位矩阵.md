# ADR-0041 · `planCapture` 的拒绝矩阵、钳位矩阵与常量归属

- 状态: Accepted
- 日期: 2026-08-05
- 相关任务卡: T-262（· T-263 · T-266 · T-267 消费）
- 相关宪法条款: C8（无显卡能测）· 铁律 12（规范没写清楚的先写 ADR）

## 背景

T-262 的卡面写着「实现 `planCapture` + 五个常量 + `CaptureRequest` / `CapturePlan` / `CaptureRejection`」，并要求「拒绝矩阵四条各一测且 `reason` 逐字断言」「钳位矩阵五条」。

**这两个矩阵的内容，规划里一处都没有。** 它们原本在 `design/render-out.md`——[ADR-0021](0021-撤销-D20-v1.0-引入后处理链.md) 逐行引用过它（`render-out.md:166` 的「`planCapture` 第 4 条」、`:427`、`:1095`），但那份领域设计**不在这个仓库里**（`find . -name 'render-out*'` 无输出）。今天能读到的只有 ADR-0021 转述的那一条（透明背景改判降级）。

所以四条拒绝、五条钳位是本卡定的，不是抄的。按铁律 12，定在这里。

## 决定

### 1 · 拒绝矩阵（四条）

判据统一：**「没有任何一张图能回答这个请求」才拒绝，能改成一张图的一律钳位。**

| # | 条件 | 为什么不能钳 | `reason`（逐字） |
|---|---|---|---|
| R1 | `format==='jpeg'` 且 `background==='transparent'` | JPEG 没有 alpha 通道。钳位只能悄悄改掉用户点的两个选项之一，改哪个都不是他要的 | `JPEG 格式不支持透明背景。请改用 PNG 格式，或把背景改为不透明。` |
| R2 | 视口宽或高不是正有限数 | 连纵横比都算不出来。这是「画面还没显示就点了导出」的真实形状 | `画布尺寸还不可用，无法导出。请等画面显示出来后再试。` |
| R3 | `scale` / `longEdge` 显式给了但不是正数，或 `longEdge < 256` | 悄悄回退到默认值会把调用方的 bug 变成一张尺寸莫名其妙的图 | `导出参数不合法：倍率与长边都必须是正数，且长边不小于 256 像素。` |
| R4 | 三条探针里最紧的一条 `< 256` | 已经没有可降的余地 | `当前显卡最大只支持 {n} 像素的画面，无法导出可用的图片。` |

R3 与 R4 共用 `MIN_EXPORT_EDGE = 256` 这一条线，两个成因（调用方传了 `longEdge: 10` / 显卡上限只剩 64）指向同一件事：**给出一张没用的图比明确拒绝更糟**，因为用户会以为导出成功了。

⚠ **「尺寸太大」不在拒绝矩阵里。** 曾经打算把它列为第四条，实测下来它永远触发不了：长边硬上限 3840 与显卡上限都是钳位，钳完之后总有一张图。硬凑成拒绝就得引入一条「不许缩小」的假设，而那条假设没有任何需求支持。

### 2 · 钳位矩阵（五条）与「必有说明」

| # | 钳位 | `notice` 里必须出现的数 |
|---|---|---|
| C1 | `scale > MAX_EXPORT_SCALE` | `4` |
| C2 | `scale > maxScaleFor(pipelineMode)` | `2`（composed）|
| C3 | 设备像素超出有效显卡上限 | 显卡上限与降到的倍率 |
| C4 | 长边超过 `min(MAX_EXPORT_EDGE, 有效显卡上限)` | 最终的宽 × 高 |
| C5 | `longEdge` 与 `scale` 同给 | 生效的长边 |

**`notice` 非空 ⇔ 计划与请求不一致。** 这条等价关系是调用方唯一需要判的东西，也是「静默钳位」唯一的机械防线：用户点了 4×、拿到一张 2× 的图、没有任何提示，他会以为是自己看错了。

C4 的两个成因给两句不同的话（合同上限 3840 / 这台机器的显卡上限）。混成一句之后用户不知道该换台机器还是该接受 3840。

### 3 · 常量六个，不是五个

卡面说「五个常量」。实现下来是六个，多出来的一个是 `MIN_EXPORT_EDGE`——没有它，R3 与 R4 两条拒绝都没有落点。逐个列明：

| 常量 | 值 | 它回答的问题 |
|---|---|---|
| `MAX_EXPORT_SCALE` | 4 | 对话框允许点到几倍（合同里的 `scale: 1–4`）|
| `MAX_EXPORT_EDGE` | 3840 | 输出图片长边的合同硬上限（拍板项 P-12）|
| `MAX_SCALE_DIRECT` | 4 | direct 管线扛得住几倍 |
| `MAX_SCALE_COMPOSED` | 2 | composed 管线扛得住几倍（ADR-0021 腿 3 的显存实测表）|
| `CONSERVATIVE_EDGE_LIMIT` | 4096 | 三条探针全报 0 时按多少算 |
| `MIN_EXPORT_EDGE` | 256 | 小到什么程度就不值得导了 |

**`MAX_EXPORT_SCALE` 与 `MAX_SCALE_DIRECT` 今天都是 4，看起来重复，但它们回答的不是同一个问题**，所以不合并。合并的代价是：改动其中任何一个语义时，另一个会被顺手一起改。

### 4 · `MAX_SCALE_*` 落在 `image-export.ts`，不落在 `render-pipeline.ts`

卡面写「`MAX_SCALE_DIRECT=4` / `MAX_SCALE_COMPOSED=2` 由 T-263 提供」，而 T-263 独占 `render-pipeline.ts` 且排在 T-262 之后。**两条路**：

- T-262 只写公式、等 T-263 落常量 → 中间这一段时间 `maxScaleFor` 没有接线，正是 X-19 点名的「两张卡各交付一半」；
- 常量落在 T-262 自己的文件里，T-263 的 `resolveExportPipeline` **import 它**（本条）。

取第二条。代价：与卡面「由 T-263 提供」这句字面不符，已登记进 `IMPL_NOTES §3`。**T-263 落地时必须 import，不许再抄一份**——抄一份就等于把「composed 上限」这件事写在两个地方，而它们会分叉。

### 5 · 长边模式不乘 `pixelRatio`

倍率模式下 `width = round(vw × scale × pixelRatio)`；长边模式下 `width = round(vw × longEdge / max(vw,vh))`，**不乘**。

不是忽略设备像素比：长边模式下用户给的目标**已经是输出图片的像素**了，再乘一次会把「3840 像素宽」的请求变成 7680。两条路径读的是同一个 `captureDevicePixels`，长边那条喂给它 `pixelRatio: 1`。

### 6 · `CONSERVATIVE_EDGE_LIMIT = 4096` 而不是 2048

WebGL2 规范下限是 2048。取 2048 的话，一台探针失灵的机器上连 1× 的 2560 宽视口都导不出来，而这正是 [T-214](../../packages/core/src/runtime/capability.ts) 那条注释警告的形状（「unknown 是老浏览器对一块完全够用的 GPU 的报告」）。取 4096 的代价写在下面。

## 代价

1. **`CONSERVATIVE_EDGE_LIMIT = 4096` 是一个赌。** 真有一台只到 2048 的机器、且三条探针全部失灵时，我们会算出一个它画不出来的尺寸，然后在导出那一刻丢上下文（现象是整个页面变白）。这个组合今天没有任何机器验证过——**G0.5-8 的目标机器 benchmark 仍未闭合（ADR-0022）**，所以 4096 和 2 一样是拍的，不是测的。

2. **`MAX_EXPORT_EDGE` 与 `MAX_EXPORT_SCALE` 互相遮蔽，而对话框不知道。** 在 1920 宽的视口上 3× / 4× 根本到不了——3840 的长边上限先咬住了，用户点 4× 拿到的和点 2× 一模一样（只多一句 notice）。T-267 的对话框如果原样列出 1× / 2× / 3× / 4×，就是列了两个够不着的档位。**这一条要传给 T-267**，本卡不改对话框。

3. **四条拒绝、五条钳位是本卡定的，不是从设计文档抄的。** `design/render-out.md` 不在仓库里，它的「`planCapture` 第 4 条」今天只能靠 ADR-0021 的转述反推。如果那份文档以后回到仓库、且它的矩阵与这里不同，**以这里为准并改那份文档**——不许两份并存。

4. **`postFxActive` 放进 `CaptureLimits` 而不是 `CaptureRequest`，意味着 `CaptureLimits` 不再是「纯硬件数字」。** 它现在混着一个运行时状态。接受的理由是导出上限确实由「机器 + 当前管线」共同决定、而用户不选管线；代价是这个类型的名字开始名不副实。

5. **纵横比的性质在极端视口上不成立。** `|w/h − vw/vh| < 0.01` 靠的是短边有足够多的像素去吸收四舍五入；`4000 × 17` 的视口缩到 256 长边时短边只剩 1 像素，比值差 20 以上。单测在真实纵横比的一大片输入上断言它，**并且不假装它对任意输入成立**。

## 撤销条件

- **`design/render-out.md` 回到仓库** → 逐条对拍两个矩阵，冲突处以本 ADR 为准并改那份文档，然后把本 ADR 的「代价 3」删掉。
- **G0.5-8 的目标机器 benchmark 闭合** → 用实测数替换 `CONSERVATIVE_EDGE_LIMIT`，并重估 `MAX_SCALE_COMPOSED`。届时代价 1 消失。
- **T-263 落地时没有 import `MAX_SCALE_DIRECT` / `MAX_SCALE_COMPOSED` 而是自己又写了一遍** → 决定 4 失效，两处会分叉。这一条应当在 T-263 的评审里机械检查（`grep -c 'MAX_SCALE_COMPOSED = ' packages/core/src` 必须是 1）。
- **出图需要 A3 印刷（长边 > 3840）** → 拍板项 P-12 被推翻，`MAX_EXPORT_EDGE`、显存预估与软渲策略要一起重评，本 ADR 的钳位矩阵 C4 重写。
