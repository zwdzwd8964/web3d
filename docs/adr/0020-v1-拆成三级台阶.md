# ADR-0020 · v1 拆成 v1.0 / v1.2 / v1.5 三级台阶

- 状态: Accepted
- 日期: 2026-08-03
- 相关宪法条款: NORTH_STAR §3（版本阶梯）、§7（指标表）、C4、C5

> ⚠ **待产品负责人确认**：三级切分本身、以及 flows / pages 两项合同能力推迟到 v1.2 交付这件事，需要产品负责人签字。本 ADR 按此撰写并据以起草 v1 规划与台账；若未获确认，v1.2 的全部内容退回 v1.5，本 ADR 标 Superseded。

## 背景

`NORTH_STAR.md:91` 的版本阶梯把 v1 写成一级台阶，`:145` 一行列了八块新增（后端、模型/材质库后端化、特效预设、渲染出图、流程管理、页面覆盖层、多媒体、权限、部署三件套）。这一行在 v0 写下时是一句范围声明，不是一次估算。

13 份领域设计稿完成后第一次有了实测：

| 口径 | 张数 | 人日 | 出处 |
|---|---|---|---|
| 13 份稿子合计 | 201 | 212.1 | `merged/backlog.md §0-1` |
| **原归属 v1.0（含外部数据源整条线）** | **147** | **≈148**（148.9） | `merged/backlog.md §1 D-1` 代价栏 |
| 按 R1 把数据源 8 张移进 v1.5 后 | 130 | 132.4 | `merged/backlog.md §6 合计行` |
| 再做「只做必须项」瘦身 | 102 | 104.5 | `merged/backlog.md §7.2` |

**瘦身只省下 27.9 人日，21%。** 而 `backlog.md §7.2` 末尾的诚实结论比这个百分比更重要：真正能无痛划出的只有 4 张 / 3.3 人日（附件B、用户手册、培训模板、体检报告呈现增强），剩下 24 张「应该」里一半划出会立刻在别的卡的验收上打洞——bench 三卡被 T-309/T-310 依赖、样板工程的爆炸剖切编排是黄金路径 III 第 7~9 步唯一可演的内容、Picker 剖切感知不做则「点击被剖掉的墙仍会选中墙」。

结论是一句话：**范围定义本身才是杠杆，不是卡的取舍。** 对照技术方案 §5.1 的原始总预算 45 人日，合并稿是 4.6 倍；即使砍到瘦身版也还有 2.3 倍。在这个量级上继续讨论「砍哪几张卡」，是在一个错误的抽象层上省钱。

与此同时，产品负责人给 v1.0 的定义是三个词：**能演示、能卖、能被嵌进别人的系统**。这三个词里没有一个需要后端、多场景、分享链接或外部数据源；也没有一个需要 flows 的线性步骤与 pages 的槽位覆盖层。

## 选项

1. **保持一级 v1。**
   - 收益：宪法一字不改；「v1 已交付」在合同语境与工程语境里是同一件事。
   - 代价：晋级门槛要同时覆盖表现力与后端，任何一条不过整版不过；schema 冻结与后端接口冻结被绑在同一个时点；按 `backlog.md §8.3` 的推算，单 agent 串行 ≈32 个工作日不间断，中间**没有任何一个可交付、可演示、可收钱的节点**——这正是 ADR-0015 当初拒绝一次吞下 v1 的同一条理由。

2. **拆两级 v1.0 / v1.5**（合并稿的原推荐，`v1-architect-memo.md §版本切分`）。
   - 收益：后端与合同材料独立成级。
   - 代价：v1.0 仍是 130 张 / 132.4 人日 ≈ 160 小时 agent 时钟（`backlog.md §8.2` 的 1.3× 保守口径），是 v0.5 的数倍；且它把表现力线与 flows/pages 编排线压在同一级里，而两条线都碰 `packages/core/src/runtime/scene-runtime.ts`（11 张卡声明独占）与 `packages/core/src/eca/types.ts`（10 张，`backlog.md §0-2`）——并行度会从 10 塌到 2~3，墙钟翻倍。

3. **拆三级 v1.0 / v1.2 / v1.5**（本条）。
   - 收益：见「决定」。
   - 代价：见「代价」。

4. **拆成 v1 / v2 并把后端推到 v2。**
   - 收益：v1 最小。
   - 代价：与合同交付期直接冲突；且 v2 的定位（「第二个客户是配置工作」）会被后端污染，`NORTH_STAR.md:161-163` 的三条门槛全部要重写。不可接受。

## 决定

选 3。版本阶梯改为：

```
v0 → v0.5 → v1.0 → v1.2 → v1.5 → v2 → v3
```

| 台阶 | 名称 | 范围 |
|---|---|---|
| **v1.0** | 地基与表现力 | 六张地基卡 · v0/v0.5 债务清偿 · schema v3 一次冻结 · 描边与雾 · 爆炸与剖切 · 渲染出图 · 播放器嵌入 SDK · 泵组样板工程 · 编辑器三条打磨 |
| **v1.2** | 编排与复用 | flows 线性步骤 · pages 槽位覆盖层 · 动画序列编排增强 · 规则模板与场景模板 · 新事件（`flowStepEnter` / `pageEnter` / `overlayClick`） |
| **v1.5** | 合同交付 | 后端全量 · `HttpApiProvider` · 服务端资产转码 · 多场景与 `goToScene` · 分享链接 · 外部数据源（功能部分）· 部署三件套 · 验收材料 |

v1.0 的范围与产品负责人的三个词逐词对应：**能演示** = 样板工程 + 表现力四件套；**能卖** = 渲染出图（效果图是销售物料）；**能被嵌进别人的系统** = 播放器嵌入 SDK。

同时定死两条随本裁决生效的约束：

1. **schema 只 bump 一次（2→3），在 v1.0 内完成**，且必须同时冻结 v1.2 与 v1.5 才用的**全部**字段。沿用 v0 对 `flows` / `pages` / `media` 的做法（`packages/schema/src/deferred.ts` 在 v0 就把形状定好）与 v0.5 的 D11。**开工后发现漏字段 → 登记 v2，不追加。** 冻结之前先出一份逐字段裁决表，六个领域各自签字（v1.0 的 T-206）——现在的做法（单方面出清单）已被证明会漏掉两个领域的全部字段。
2. **编号分配**（`v1-architect-memo.md §编号分配` 基础上按三级台阶重排）：任务卡 v1.0 = T-200~T-299 · v1.2 = T-300~T-359 · v1.5 = T-400 起；里程碑 v1.0 = M14~M18 · v1.2 = M19~M21 · v1.5 = M22~M27；设计决策 D21 起 · ADR 0020 起 · 完整性检查 I16 起 · 晋级门槛 G1.0-n / G1.2-n / G1.5-n · schemaVersion 3。

本 ADR 修改 `NORTH_STAR.md §3` 的版本阶梯图与 v1 条目，`CLAUDE.md` 的「当前活动版本」与必读文档表随之更新。

## 代价

明确接受七条：

1. **多一级台阶 = 多一次晋级门槛与一次收尾审查的固定成本。** v0.5 的收尾审查（E18，T-180~T-186）本身是 7 张卡的投入，且这是制度性的、不能省的（`MVP_V0_5_进化规划.md §6` 已把「每个里程碑收尾一轮对抗式审查」写进流程）。G1.2-n 这一整套门槛表、一份独立台账、一次指标快照，都是纯管理开销，不产出任何用户可见的东西。

2. **合同交付面在 v1.0 结束时仍不完整。** flows（「流程管理」）与 pages（「页面覆盖层」）是合同 18 项里的**两项**，推迟到 v1.2 意味着 v1.0 交付时这两项一行代码都没有。对外说「v1.0 已交付」会被理解成「合同项已交付」，措辞必须逐项区分——这不是文案问题，是收款节点的定义问题。

3. **v1.0 要为一批自己不用的字段付出成本。** schema 一次冻结意味着 `flows` / `pages` / `prefabs` / `dataSources` 的完整性检查、五个遍历面、fixture、迁移表在 v1.0 就要全部到位，而 v1.0 自己一个都不消费。这部分工作在 v1.0 的验收里表现为「一堆没人用的测试」，很容易在赶工时被当成脂肪砍掉——砍了就会在 v1.2 第一次写入时铸 id 撞车、发布漏字节。

4. **「v1」这个词在合同语境与工程语境里彻底不是同一个东西。** 此后任何一份文档写「v1」都必须补出是哪一级，历史文档（IMPL_NOTES、METRICS、勘察记录）里已有的「v1」全部变成歧义词。

5. **编号预留可能不够。** v1.2 只有 T-300~T-359 六十个号位；若 flows/pages 的实际卡数超编，要么挤进 v1.5 的号段、要么开一段不连续的号，两者都让「编号连续，只增不改」这条纪律出现一个洞。

6. **v1.0 与 v1.2 之间会出现一批「半条能力链」。** 典型的是「新建项目」——v1.0 要有一个不依赖模板机制的项目入口，v1.2 再把模板网格接上去（见 ADR-0023）。第二次做时要改第一次的 UI，返工面约半张卡。这是明确接受的重复，不是疏漏。

7. **估算本身的不确定性没有被这次切分消除。** `backlog.md §8.2` 说得很直白：v0.5 的校准样本只覆盖 0.5~0.8 人日的小卡，而 v1 有大量 ≥1.5 人日的卡（合并稿口径 47 张 / 96.6 人日 / 47%；三级切分后的台账口径是 **68 张 / 122.6 人日 / 56%**，见 TASK_BACKLOG_V1 附录 C.3）**完全没有校准数据**，大卡的 agent 时钟大概率不是线性的。切成三级让每一级的估算误差小一些，但没有让总误差变小。

## 撤销条件

- v1.0 收尾时 flows / pages 的实际范围萎缩到 5 张卡以内 → 并回 v1.0 的收尾波次，作废 G1.2-n，阶梯退回两级。
- 合同交付期被提前到 v1.2 之前 → 三级合并回两级，v1.2 全部内容并入 v1.5，本 ADR 标 Superseded 并重写门槛表。
- v1.0 的实际耗时超出估算 2 倍（`CLAUDE.md` 停工条款第 6 条）→ **停下来重新切分，不是继续按台阶走**。一个已经证明估不准的切分，继续执行只会把误差带进 v1.2。
- 产品负责人否决三级切分 → 按上面的醒目标记执行：v1.2 退回 v1.5。
