# ADR-0017 · 原始体沿用 three 的默认朝向，分段数固化在 core

- 状态: Accepted
- 日期: 2026-07-31
- 相关宪法条款: C1（状态进文档）
- 相关任务卡: T-140（PrimitiveFactory）、T-142（拖拽放置依赖包围盒）

## 背景

进化规划 §4.1.2 冻结了七种原始体的字段，**只有语义尺寸**：`plane` 是 `width` / `height`，
`cylinder` 是 `radiusTop` / `radiusBottom` / `height`，等等。规范没有说这些几何体**朝哪个
方向**，也没有说细分程度。

两件事都必须在 T-140 定下来，而且都是**改不回来的**：朝向变了，已有文档里每一个 plane
的观感都变；分段数如果进了文档，同一份文档在两个 core 版本下会长得不一样。

`plane` 尤其含糊：three 的 `PlaneGeometry` 在 XY 平面（朝 +Z），而 Unity / Blender 里的
"平面"通常是地面（XZ）。字段叫 `width` / `height` 又更像屏幕坐标的说法。

## 选项

### 朝向

1. **沿用 three 的默认朝向**：plane 在 XY 朝 +Z，cylinder / cone / capsule 沿 Y 轴。
   - 收益：字段名与 three 的构造参数逐字对应（`width`/`height`、`radiusTop`/`radiusBottom`），
     说明规范就是照着它抄的；七种体的规则统一，不需要记"哪个被转过"。
   - 代价：想要地面的用户必须自己转 90°。
2. **plane 特殊处理，烘进 -90° 的 X 旋转当地面**。
   - 收益：拖出来就是地面，符合多数建模软件的直觉。
   - 代价：**这个旋转不在文档里**。用户在属性面板看到 rotation 是 0，gizmo 却显示一个躺平的
     面；他把 rotation 归零，什么也不会发生。这是一份看不见、改不掉的隐藏状态（违 C1 精神）。
     而且七种体里只有一种被转过，是需要记住的例外。

### 分段数

1. **固化在 core**（sphere 32×16、cylinder/cone 32 段、torus 48×16、capsule 16×8）。
   - 收益：文档只描述"是什么"，不描述"画多细"；同一份文档在任何 core 版本下语义一致。
   - 代价：用户无法为了性能把球调粗糙；真需要时只能换成导入模型。
2. 放进 schema 当字段。
   - 收益：可调。
   - 代价：给了用户一个**只能把画面变慢**的旋钮，且它是渲染实现细节——与色彩空间不进文档
     （MVP 规划 D3）是同一类问题。加字段还要走一次 schemaVersion 迁移。

## 决定

朝向选 1，分段数选 1。**七种原始体全部沿用 three 的默认朝向与位置（几何中心在原点），
分段数写死在 `primitive-factory.ts`。**

想要地面的用户把 plane 转 90°，这个旋转**落在文档的 `transform.r` 里**——看得见、能撤销、
发布出去还是它。

## 代价

明确接受三条：

1. **拖出一个 plane 得到的是竖着的面，不是地面。** 多数用户的第一直觉会落空一次。缓解手段
   在编辑器侧（库面板的缩略图照实画，T-141），不在几何上。
2. **球体在特写下能看出多边形。** 32×16 在展台尺度够用，怼到脸上会露馅。真需要更细的，
   属于"该用导入模型"的场景。
3. **分段数以后要调，是改 core 的行为**，会让同一份老文档的三角面数变化——bench 的历史
   数据因此不可跨版本直接比较。调的时候要在 BENCHMARK.md 里标注版本。

## 撤销条件

出现下列任一信号时重新考虑：

- 用户实测反馈里"平面朝向不对"成为高频抱怨（此时正确的修法是**在编辑器创建时写一个显式的
  旋转进文档**，而不是把旋转烘进几何——那仍然违反本 ADR 的理由）；
- 弱机实测（H3 / T-174）显示原始体的三角面数是瓶颈，需要按场景调细分；
- 规范后续正式定义了朝向或分段字段——以规范为准，本 ADR 作废。
