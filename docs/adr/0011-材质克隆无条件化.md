# ADR-0011 · 材质写时复制改为无条件克隆

- 状态: Accepted
- 日期: 2026-07-30
- 相关宪法条款: C1；相关设计决策: D3；相关风险: R08

## 背景

MVP_V0 D3 把写时复制描述为三步：

> 1. 若该节点无 material override → 直接用源材质；
> 2. 若有 override 且源材质被 **>1 个 Object3D 引用** → clone 一份…；
> 3. 引用计数归零时 dispose。

第 2 步的条件是一个优化：源材质只被一个 mesh 用时，就地写不会影响别人，还能少一个
draw call 批次。

实现后 `material-registry.test.ts` 的一条测试抓到它不成立：

```
两个节点都覆盖同一个材质定义，applyAll 顺序处理：
  节点 A：countUsers = 2  → 克隆，A 用克隆体
  节点 B：countUsers = 1  → 判定"未共享"，直接写进资产的原始材质  ← 污染
```

更根本的问题是：**资产的材质属于资产缓存**，同一个 GLB 可能被多个文档、多个场景引用
（甚至同一编辑器里的两个项目）。就地写它，污染范围超出了当前文档，而 D3 的条件里
没有这一层。

## 选项

1. 保留条件，但在克隆后把源材质标记为"仍被逻辑引用"以稳住计数 —— 修掉了顺序问题；
   没修掉资产缓存被污染的问题。
2. 按材质定义 id 共享一个克隆体（两个节点覆盖同一定义 → 共用一份）—— draw call 最省；
   但 T-040 的高亮走同一条路径，共用克隆体会导致"高亮一个零件，同定义的另一个也亮"。
3. 无条件克隆，每节点一份。资产材质永不被写。

## 决定

选 3。`MaterialRegistry.materialFor` 不再做引用计数判断；
`countUsers` 保留为公开工具函数（诊断与测试用）。

## 代价

- Draw call 批次比 D3 设想的多：覆盖了材质的节点各占一份材质实例。
  上限是"用户显式覆盖过材质的节点数 + 被高亮过的节点数"，实际场景里是个位到几十，
  与几百个共享同一钢材质的零件不在一个量级——但这是真实成本，不是零；
- 与 D3 的字面文本不符——**这一点随本 ADR 一并被接受**（状态栏即是那次确认），
  D3 在这一处的措辞由本 ADR 取代；
- 克隆体的 dispose 责任全在注册表，漏一处就是显存泄漏。已由 `dispose()` 与
  移除覆盖时的即时 dispose 覆盖，并有单测断言 `cloneCount` 归零。

## 撤销条件

若 benchmark（T-110）显示材质实例数成为真实瓶颈，改用选项 2 的"按定义共享克隆体"，
**同时**把高亮改成不写材质的实现（例如 v1 的 OutlineEffect，它本来就不碰材质）。
两件事必须一起做——只做前者会立刻引入"高亮串台"的可见 bug。
