# ADR-0029 · 变量变化的跨 `await` 循环防线（ChurnGuard）

- 状态: **Accepted**
- 日期: 2026-08-03
- 相关宪法条款: **C5**（扩展靠注册表，不靠改引擎）· **C8**（引擎可脱离 GPU 测试 · 时间必须可注入）· NORTH_STAR §4 的 **Q4**
- 承接卡: **T-204**
- 前一次同类破例: [ADR-0018](0018-withCurrentEvent-改用-Proxy-委托.md)（`engine.ts` 的逐方法委托改 Proxy）

> **这是 v1 全程对 `engine.ts` 的唯一一次合法改动**（另一个文件 `executor.ts` 的那一次是 T-203 / [ADR-0028](0028-refkind-注册表化.md)）。除这两处外，两个文件的 diff 必须为 0。

## 背景

`MAX_CHAIN_DEPTH = 16`（`engine.ts:26`）是 ECA_SPEC §9.2 **B10** 的全部实现。它数的是 `dispatch` 的**同步嵌套深度**：`chainDepth++` 在进入时、`chainDepth--` 在 `finally` 里。

**同步嵌套深度只在整条链是同步的时候才等于「链有多长」。**

一旦规则的 `then` 里出现任何一个 `await`——`wait`、`playAnimation(await:true)`、`playMedia`、任何返回 Promise 的动作——那次 `dispatch` 就已经返回了，`finally` 已经把 `chainDepth` 减回去了。下一次变量变化是从一个干净的栈上重新进来的，深度永远是 1。

实测复现（本卡的测试就是它）：两条互相写对方变量的规则，`then` 里各加一个 `wait(1)`，跑 300 轮**零告警、不收敛**；把 `wait` 去掉的对照组恰好在第 16 层报一条。

**那条 B10 单测为什么是绿的**：它的 `then` 里恰好只有一个 `setVariable`，没有 await。测的是同步那一半，而同步那一半本来就是对的。

三件事让它比一般缺陷更值得单独一张卡：

1. **它是引擎的既有洞，不是某个功能的副作用。** 因此归 v1.0 债务清偿，不随外部数据源滑到 v1.5。
2. **它在编辑器里的表现是整个页面卡死**，而这是作者最容易写出来的一类错误——「A 变了就把 B 设成 A+1」是配置界面上完全自然的两步操作。
3. **v1.2 的 flows 会把它的可达性放大一个量级**：`nextStep` → 写流程变量 → `variableChange` → 规则 → 可能又 `nextStep`，而流程动作天然要 await。回归卡是 T-314。

## 选项

### 选项 1 · 不做，把 `MAX_CHAIN_DEPTH` 的局限写进文档

- **收益**：`engine.ts` diff 为 0，不需要这份 ADR。
- **代价**：B10 这条规范承诺「有循环保护」，而它对**带 await 的环**（也就是 v1.2 之后的主要形态）完全无效。一条只在一半情形下成立的安全承诺，比没有承诺更坏——它会让人不再去想这件事。且现象是页面卡死，用户唯一的出路是关标签页，工作全丢。

### 选项 2 · 把 `chainDepth` 改成跨 `await` 传递（异步上下文追踪）

- **收益**：概念上最贴近「链有多长」这个原意。
- **代价**：要么引入 `AsyncLocalStorage`（Node 专有，浏览器没有，直接违 C2/C8 的可移植前提），要么把一个 chain id 手工穿过 `execute` → `runStep` → 每个动作 handler → `ctx.setVar`，**那是把「我是谁触发的」写进每一个动作的签名**——这正是 C5 要避免的形状：引擎的内部概念泄漏到每一个扩展点上。

### 选项 3 · 每变量的变化频率上限（滑动窗口）——**采纳**

- **做什么**：`ChurnGuard.tripped(variableId, nowMs)`，窗口 `CHURN_WINDOW_MS = 1000`、上限 `CHURN_LIMIT = 240`；在 `dispatch` 里紧接 `MAX_CHAIN_DEPTH` 判定之后调用，命中则记一条 error 并 `return`。
- **收益**：**判据不依赖调用栈的形状**，所以同步环与跨 await 环一视同仁。实现是一个 Map 加一次剪枝，零新增依赖，时间走 `ctx.now()`（C8 不破）。两条防线各管一件事：深度管「一次事件炸开多宽」，频率管「一秒之内变了多少次」。
- **代价**（见下）。

## 决定

**采纳选项 3。**

1. 新增 `packages/core/src/eca/churn-guard.ts`：`CHURN_WINDOW_MS = 1000` · `CHURN_LIMIT = 240` · `tripped(variableId, nowMs)`，**越限的那一次且仅那一次返回 true**。
2. `EcaEngine.dispatch` 在 `MAX_CHAIN_DEPTH` 判定之后插入一次调用，仅对 `variableChange` 事件；命中则 error 日志 + `return`。
3. `detach()` 与 `setEnabled(false)` 清计数器。
4. ECA_SPEC §9.2 的 B10 改写成两句（深度 16 同步链 **加** 每变量每秒上限），并**明写接受的代价**（见下第 1 条）。
5. 时间一律 `ctx.now()`。ECA 里不许有真实时间（铁律 6），而这条防线本身是关于时间的——它是最容易在这一点上出错的一张卡。

## 代价

1. **它只拦失控环，不拦慢环。** 每秒 239 次的环不会被拦住——它不是失控，它是慢。这条代价是明写并接受的：一个把阈值压到「不可能误伤」的防线会误伤真实场景（下一条），而一个把阈值抬到「绝不漏」的防线会拦掉合法的高频数据源。**240 这个数字是拍的，不是测的**——它来自「16 ms 一帧、每帧最多写 4 次」这个手算，没有目标机器数据支撑（G0.5-8 未闭合）。
2. **误伤的形状是真实的**：v1.5 的外部数据源如果配了一个 100 ms 轮询、每次写 3 个变量的联动链，单变量频率可以逼近这个上限。届时用户看到的是「规则突然不跑了」加一条中文 error。缓解手段是那条 error 的措辞必须说清是**频率**被拦而不是规则出错——因此测试断言到措辞，不断到「打了 error」（v0.5 T-186「两条守卫互相掩护」的直接对策）。
3. **这是 `engine.ts` 的第二次改动**，而每一次改动都在削弱「这个文件不该被改」这条规矩的说服力。ADR-0018 那次是委托机制，这次是一道防线，两次都不含任何动作知识（C5 的实质没有被破），但**次数本身要记账**：第三次要求改 `engine.ts` 的卡出现时，应当先问「是不是引擎的抽象漏了」而不是先写第三条 ADR。
4. **计数器是引擎级的，不是文档级的。** 它不进文档（运行时瞬态，C1），因此**预览与播放器各有一份独立计数**。同一份文档在两侧的拦截时刻可以不同——parity 比较的是 `ExecResult` 序列，而被拦下的那次 dispatch 不产生 `ExecResult`，所以**理论上两侧可以在这里分叉**。今天不会发生（两侧时钟在 parity 里是同一个注入时钟），但这是一条真实的 C3 张力，记在这里。

## 撤销条件

- **目标机器 benchmark（G0.5-8 / H1）给出真实的每秒变量写入上限**。届时 240 这个拍出来的数字应当被实测数字替换，或者被证明量级正确后升格为「已测」。
- **出现第一次误伤**：一个合法场景被拦。此时先看措辞是否让用户理解了发生了什么，再决定是抬阈值还是给数据源单独一条豁免路径——**不许直接把上限调大了事**，那会让这条防线走上「例外没有到期日」的老路（NORTH_STAR §8）。
- **第三张要求改 `engine.ts` 的卡出现**。按代价第 3 条，那时要重新评估的不是这条防线，是引擎的抽象边界。
